## SEMANTIC_CONTRACT_AND_FAILURE_CONTAINMENT

- V2 is additive and opt-in behind a repository-conventional local pipeline selector (exact key to be selected after config inspection); default remains v1 until architecture and acceptance pass. No data migration is planned.
- V2 schema failure after one repair is explicit failure for that V2 run. It cannot be converted to a successful V1 result invisibly. Operator can explicitly choose V1 for rollback.
- Only a confirmed parse/schema validation error is eligible for exactly one schema-only repair. Provider/transport/timeout/cancellation/generation errors are explicitly classified and fail immediately; a repair-generation error also fails immediately. They are never reported as schema repair success/failure without that distinction.
- Requiredness is assigned only by trusted template policy or an explicit caller-supplied selected-claim target; LLM-produced labels and claim ordering have no authority. All other claims are optional/non-gating candidates. Evidence absence/conflict is scoped to the affected claim/section; a selected/required claim can fail only its mapped section or selected-claim acceptance, never an unrelated section or whole run by default. Every required causal/conditional claim is checked independent of whether its opaque claim ID is included in prose.
- Every asserted/renderable claim must resolve evidence against immutable raw transcript occurrences. The extractor supplies an exact raw quote (or validated offsets); runtime resolves it to a unique absolute character interval using exact matching and source-chunk origin offsets. Repeated, missing, malformed, corrected-only, or mismatched quotes remain unresolved. No fuzzy search, fabricated offset, or raw quote is written to tracked diagnostics.
- R4 same-evidence identity requires validated non-empty overlap between absolute raw-source occurrence intervals plus a typed material incompatibility. A shared coarse chunk ID or one shared context phrase is insufficient. A conflict remains explicit without a winner and is contained to its claim/section dependencies; optional conflict cannot globally veto.
- A failed targeted patch is rolled back byte-for-byte to the last accepted section. No semantic validator failure is “fixed” by weakening policy.
- Finalizer output is not trusted by virtue of validated pre-finalizer sections. Acceptance runs against the exact post-finalizer complete record; decisive required coverage loss, unsupported high-risk additions, required source-tag loss, or confirmed cross-section duplication cannot be diagnostic-only. Optional or uncertain findings remain local and cannot veto.
- Novelty detection is conservative and source-derived: only decisive exact/boundary-aware high-risk mismatches become blocking. Ambiguous normalization, Chinese/Arabic numeric forms, verified aliases, or weak term/similarity matches remain `UNKNOWN/AMBIGUOUS` diagnostics, preserving false-positive-safe continuation.
- A profile selection requires ≥3 distinct observed invocations per candidate (N≥5 preferred), with valid evaluator-backed overall score, hard-fail, causal/attribution, faithfulness, traceability, completeness, and usability dimensions on every run; output strings need not differ between invocations. No missing metric is imputed as zero. Unsupported or incomplete candidates are ineligible and only affect profile/quality acceptance.
- Cloud path and shared semantics are frozen; any unavoidable shared helper change requires a cloud golden/contract regression demonstrating unchanged behavior.

## TARGET_CONTRACT

1. `EvidenceSpan`: stable span ID, optional speaker/time metadata, raw text, optional corrected text, source SHA-256, and absolute raw-transcript character origin/range sufficient to map overlapping chunks to the same source offsets. Full text is runtime/local-cache only and gitignored.
2. `FactClaim`/`FactLedger`: normalized typed claims, explicit status/uncertainty, explicit subject-predicate-object and polarity; relation type includes causal/conditional/temporal; numeric/date/attribution fields; one or more evidence refs with exact raw quote or source offsets. Runtime-resolved occurrence intervals are derived from raw text, not trusted model labels. Validate structure without treating uncertain optional facts as globally invalid.
3. `ClaimConflict`: stable IDs, conflicting claim IDs, validated occurrence references/overlap and conflict type; deterministic detection; no automatic winner. Same chunk alone never establishes same evidence.
4. Trusted `TemplateClaimPolicy` and `SectionPlan`: section ID/title, required/optional claim IDs and evidence occurrence IDs. Policies separate structural fields from source-present content slots and are defined for all active templates (`general`, `section_meeting`, `procurement_evaluation`, `isms_monthly`) from their existing production definitions/prompts. For C1 only, the user attachment supplies target identity and designated raw input; an ignored private artifact may supply an untrusted locator/hash link, never trusted authorship or relation truth. Preflight resolves one exact occurrence in that raw input and derives the expected normalized relation directly from it; only then pass a privacy-safe evaluator target in memory through the real `TaskProcessor`→`SummarizationService`/V2 path, for final deterministic validation only and never to model prompts or persisted task schema. If preflight is inconclusive, do not issue/count a C1 acceptance model call; report scoped `BLOCKED/AUTHORITY`. Unclassified source-grounded candidates default optional; detected required-candidate omissions produce a section-scoped gap. Render only that section with allowed validated claims plus resolved source spans and assemble in template order.
5. `SectionQualitySnapshot`: required/covered claims, unsupported high-risk values, relation/attribution issues, duplicate claim IDs and source-trace completeness. Compare structured expected relation (subject/predicate/object/polarity/condition) with raw evidence ordering and rendered relation metadata; do not test opaque claim-ID substring membership in prose. Candidate acceptance is non-regressive on all CORE dimensions.
6. `QualityPolicy` is model-independent. `ModelRuntimeProfile` is separate from policy. Runtime capability is detected from the active backend/loaded instance, not guessed from model-name substring.
7. Diagnostics add source raw/corrected metadata, structured extraction/schema status, evidence-resolution status, ledger pre/post-consolidation, section planning/render/validation, patch/rollback, assembly/final validation/selection; tracked values are IDs, hashes, counts, safe profile metadata, status and verdict only. Evidence quote text and raw payloads stay out of tracked artifacts.
8. Final-output validator result, required coverage, cross-section duplicate results, verified source-tag anchors/diversification, and high-risk novelty findings are computed on exact post-finalizer bytes. Scan final text for numeric/date/attribution/relation candidates and likely entity/name candidates; reconcile against allowed claims, raw source and verified mappings. Block only decisive unsupported high-risk additions or mapped-required loss; ambiguous candidates remain diagnostics. Persist only redacted counts/status/IDs/hashes in tracked evidence; finalization that changes protected content must be detectable before success is returned.
9. Runtime/extraction failure classification distinguishes schema parse/validation from generation/provider/transport/timeout/cancellation. Profile sample metadata records unique observation identity or equivalent non-replay assurance, count, all required dimensions, medians/worst/ranges/hard-fail count and eligibility reason without persisting private meeting content.
