- 逐階段差：ASR −0.1、diarization +0.3、校正 **+6.8**、extraction **+11.7**、final **+4.5**、DOCX +0.7。

## 7. 使用者可立刻改善的項目（依槓桿排序）

1. **換生成模型（最大槓桿）**：改用 MoE/A3B 類（如 `qwen3.6-35b-a3b-splash`）做逐字稿校正＋生成。同機實證：整場 303.9 s（含 20 次呼叫）vs gemma 1218.6 s → **−75%**。（ML22:1050；LMS22:5010/5228/5396）
2. **改用雲端做「生成」階段**：C5 的 Gemini 生成 3 次只花 47.1 s（vs gemma 2 次 738.8 s）；整場 536.4 s。但記得**校正階段也要一起換**，否則本地校正仍吃掉 320.4 s。（C5L:90/91/95）
3. **精簡語意校正**：12 次小呼叫在 gemma 要 311.5 s、在 qwen 只要 33.8 s。可行手段：減少/合併呼叫、或指定小模型（4B–8B 級）專職校正。（D1L:38→87；ML22:968→1015）
4. **避免補強輪重送全量提示**：E1 兩輪 = 970.4 s。改成 diff／增量補強，或把每輪提示縮到「僅問題段落＋對應轉錄片段」。（E1L:109/110、123/124）
5. **提高提示快取命中**：大呼叫 `cached_tokens=0`（D1/LMS23 @01:43:30、01:49:17）。把呼叫間**共用前綴**（系統提示＋轉錄稿）順序固定、避免前綴漂移，可回收部分 prefill（D1 生成階段 prefill 423 s）。
6. **降低 context 設定**：現為 71,936（自動配置後）；滿載 KV 約 5.5 GiB（81,920 B/token × 71,936，LMS23:5048）。降到 24–32k 可減 KV 與記憶體壓力（working set 37.44 GiB／48 GB 機）。注意：縮 ctx 不會直接減少既有 13–20k 提示的 prefill 量，主要效益在記憶體與長場穩定性。
7. **善用並行**：LM Studio 實例已開 `parallel: 4`（model_snapshot），但 backend 全序列（D1L:38→43）。讓分塊（chunk）生成並行可縮短生成牆鐘（先例：手動場 4 chunks 流程，ML22:1045）。

9. **不要花時間調「GPU offload」**：此路線是 MLX 後端、統一記憶體，權重全在 GPU 上，沒有 llama.cpp 式 offload 比例可調。[INFERRED]
