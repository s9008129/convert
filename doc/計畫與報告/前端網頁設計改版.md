# 前端網頁設計改版提案 —— 蘋果 × 現代 × 簡約 × 政府專業感

> **版本**：v1.1（2026-07-08）
> **狀態**：✅ **已批准並實作（v4.3.0）**——含批准時的三項微調：①版面以 16:9 設計（容器 1120px、步驟 1 左右並排）②下載按鈕文字不換行、次按鈕對齊 ③錯誤文案改「請聯絡系統管理員」
> **依據**：Apple 人機介面指南（HIG）、美國政府設計系統（USWDS）、英國 GOV.UK 設計系統、NN/g 精靈式流程研究、數位發展部「網站無障礙規範 2.0」（政府網站須達 AA 等級）
> **範圍**：僅前端視覺與互動（index.html / style.css / app.js 的呈現層），**不動任何後端邏輯與 API**

---

## 一、一句話說明這次改版

把現在「消費 App 感」的介面（漸層字、emoji 圖示、發光按鈕），改成**像 Apple 官網一樣乾淨、像政府公文一樣可信**的介面——同時把非技術同仁會卡住的地方（不知道流程走到哪、三顆按鈕不知道按哪顆）一併解決。

---

## 二、現況問題盤點（為什麼要改）

| # | 現況問題 | 影響 |
|---|---------|------|
| 1 | 標題用藍青**漸層字**、按鈕帶藍色光暈陰影 | 消費 App 感，與公務情境不符 |
| 2 | 圖示全部用 **emoji**（📁🔒☁️⬇️❌） | 每台電腦長相不一；螢幕報讀器會唸出雜訊 |
| 3 | 三顆下載按鈕**全部同樣醒目**（藍底） | 使用者不知道該按哪顆；機關最常用的其實是 Word |
| 4 | 次要文字色 `#86868B` 對比僅 3.5:1 | **不符政府網站無障礙 AA 要求**（需 ≥4.5:1） |
| 5 | 排隊卡與進度卡是兩個區塊互相切換 | 畫面跳動，使用者以為出錯了 |
| 6 | 使用者**看不到流程全貌**（上傳→處理→下載） | 不知道自己在第幾步、還要等多久，容易焦慮 |
| 7 | 狀態只靠**顏色**區分（綠字/橘字/紅字） | 色弱同仁無法辨識；不符無障礙規範 |
| 8 | 上傳區只能滑鼠點擊，**鍵盤操作不了** | 不符無障礙「全鍵盤可操作」要求 |

## 三、設計原則（Apple HIG × 政府設計系統的交集)

1. **清晰（Clarity）**：文字任何尺寸都易讀；圖示改用單色線條 SVG（內嵌、不外連）。
2. **謙遜（Deference）**：介面為內容服務——去漸層、去光暈、去 hover 位移，改用「白卡片＋細邊框＋極淡陰影」。
3. **層次（Depth）**：用「淡灰背景 → 白色卡片 → 藍色強調」三層明度表達層級，不靠重陰影。
4. **政府專業感**：按鈕用圓角矩形（不用全膠囊）；狀態一律「圖示＋文字＋顏色」三重表達；一個畫面只有一個主要行動；文案直接明瞭（「將會議錄音拖曳到這裡」）。

## 四、視覺規格

### 4.1 色彩系統（全部通過無障礙 AA 對比檢核）

主色捨棄 Apple 消費藍，採 **USWDS 政府藍**（更深、更穩、白字按鈕對比 7.1:1）：

| 用途 | 色碼 | 說明 |
|------|------|------|
| 主色（按鈕/連結/進度條） | `#005EA2` | 政府藍，hover 加深為 `#1A4480` |
| 選取底色/資訊底色 | `#D9E8F6` | 淡藍 |
| 頁面背景 | `#F5F6F8` | 近 Apple 官網的淡灰，微冷調更顯正式 |
| 卡片 | `#FFFFFF` ＋ `1px #E2E4E8` 細框 | |
| 主文字 | `#1D1D1F` | 對比 >15:1 |
| 次要文字 | `#55565B` | **修正現有不合格的 `#86868B`** |
| 成功 | 字 `#216E1F`／底 `#ECF3EC` | 配勾號圖示 |
| 錯誤 | 字 `#B50909`／底 `#F4E3DB` | 配警示圖示 |
| 處理中 | 字 `#1A4480`／底 `#D9E8F6` | 配旋轉圖示 |

### 4.2 字體系統（內網零外連）

```css
font-family: system-ui, -apple-system, "Segoe UI",
             "Noto Sans TC", "PingFang TC",
             "Microsoft JhengHei", "微軟正黑體", Arial, sans-serif;
```

- Windows 公務機自動用 Segoe UI＋微軟正黑體；Mac 自動用蘋果系統字，兩邊都是原生質感。
- **中文排版鐵則**：正文最小 16px、行高 1.7（中文筆畫密，行高要比英文網站大）、不用斜體、不加字距。

| 層級 | 規格 | 用途 |
|------|------|------|
| 頁面標題 | 32px／粗體 700 | MeetingScribe |
| 區塊標題 | 20px／半粗 600 | 選擇處理模式、處理進度 |
| 卡片標題 | 17px／半粗 600 | 方案 A／方案 B |
| 正文 | 16px／常規 400／行高 1.7 | 說明文字 |
| 輔助 | 14px | badge、提示 |
| 頁尾 | 13px | 版本號 |

### 4.3 間距／圓角／陰影

- 間距走 8pt 網格（4/8/12/16/24/32/48px）；卡片內距統一 24–32px。
- 圓角收斂：badge 6px、按鈕 10px、卡片 14px（現在的全膠囊按鈕改為圓角矩形）。
- 陰影大幅減淡：卡片只用 `0 1px 2px rgba(16,24,40,.05)`，輪廓靠細邊框。
- 動效 150–250ms，並尊重使用者的「減少動態效果」系統設定。

## 五、版面改版重點（三步驟流程）

### 頂部常駐「流程步驟列」（新增，本次改版核心）

```
  ① 設定與上傳  ──────  ② 處理中  ──────  ③ 完成下載
```

無論在哪一步，使用者都看得到全貌、知道自己在哪裡（NN/g 研究：預見整段流程可大幅降低等待焦慮）。

### 步驟 1：設定與上傳

- 模式選擇改為標準**單選卡**：選取態＝藍框＋淡藍底＋右上角勾號；並支援鍵盤選取。
- 拖放區為視覺主角：實線淡框、拖入時變藍框淡藍底（去掉放大動效）；**補上鍵盤操作**（Tab 聚焦後按 Enter 選檔）。
- 文案改行動指引：「將會議錄音拖曳到這裡，或點擊選擇檔案」。

### 步驟 2：處理中（排隊＋進度合併為一張卡）

- 上方：四段小步驟（上傳→轉錄→摘要→完成），圓點內含數字、完成變勾號。
- 中間:進度條（單色政府藍、8px 高）＋百分比＋目前動作說明。
- 下方：排隊位置／預估剩餘時間（次要資訊列）。
- 畫面不再於「排隊卡/進度卡」間跳動。

### 步驟 3：完成下載

- 綠色勾號（48px）＋「處理完成」＋處理耗時。
- **下載按鈕分主次**（解決「三顆都很藍」）：
  - 主按鈕（藍底白字）：**下載會議紀錄 (Word)** ← 機關最常用
  - 次按鈕（白底細框）：下載 Markdown、下載逐字稿
  - 文字按鈕：重新開始
- 失敗時同位置顯示：警示圖示＋白話原因＋「重新開始」。

## 六、無障礙檢核（數位發展部規範 2.0，AA）

- [x] 一般文字對比 ≥ 4.5:1（修正 `#86868B`）
- [x] 元件邊框／focus 框對比 ≥ 3:1，所有互動元件有清楚的鍵盤聚焦樣式
- [x] 全鍵盤可操作（上傳區、模式卡補 Tab/Enter 支援）
- [x] 狀態「圖示＋文字＋顏色」三重編碼，不只靠顏色
- [x] 進度更新對螢幕報讀器友善（aria-live）、錯誤即時通報（role=alert)
- [x] 點擊目標 ≥ 44×44px
- [x] 尊重「減少動態效果」與 Windows 高對比模式

## 七、實作範圍與成本

| 項目 | 說明 |
|------|------|
| 動的檔案 | `frontend/index.html`、`frontend/css/style.css`、`frontend/js/app.js`（呈現層） |
| 不動的東西 | 後端 API、處理流程、WebSocket 協定、所有功能行為 |
| 新增資產 | 內嵌 SVG 圖示（約 10 個，直接寫在 HTML 內，零外連） |
| 預估工時 | 一個工作階段內可完成（含自測） |
| 風險 | 低——純呈現層；功能行為有既有測試護住；改版後仍會用瀏覽器實測三步驟流程 |
| 部署 | 前端是 volume 掛載，遠端 `git pull` 即生效，**免 rebuild、零下載** |
