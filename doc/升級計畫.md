## 1. 前言：這份計劃是什麼？

### 1.1 給非技術人員的說明

想像一下，您有一段一小時的會議錄音，希望電腦能夠：
1. **聽懂**：把語音轉成文字（逐字稿）
2. **理解**：從雜亂的對話中整理出重點
3. **輸出**：產生結構清晰的會議記錄

這就是我們的「MeetingScribe」專案在做的事情。

但目前我們遇到了一些問題：
- 🔴 **長錄音轉不好**：超過一小時的錄音，常常出現重複的句子
- 🔴 **整理的結果不對**：AI 整理出來的會議記錄，格式怪怪的，而且重點常常抓錯

這份計劃就是要解決這兩個問題，讓系統變得更可靠。

### 1.2 升級目標

| 目標 | 現況 | 升級後預期 |
|------|------|------------|
| 長語音轉錄品質 | 重複字樣嚴重，失真率高 | 錯誤率降低 50% 以上 |
| 會議記錄格式遵從性 | 格式不一致，常偏離主題 | 100% 遵循指定格式 |
| 跨平台支援 | 設定分散，切換困難 | 一個設定檔，全平台通用 |

## 2. 現況分析：我們目前遇到什麼問題？

### 2.1 痛點一：語音轉錄的「鬼打牆」現象

**現象描述**：  
當處理超過 1 小時的長音檔時，Whisper-medium 模型會產生「幻覺」（Hallucination），最明顯的症狀是：

- ❌ 同一句話不斷重複（例如：「謝謝大家謝謝大家謝謝大家...」）
- ❌ 出現完全不存在的內容（例如憑空出現「感謝收看」、「訂閱頻道」等字樣）
- ❌ 在靜音段落產生錯誤的填充文字

**根本原因**：
1. Whisper 的自迴歸架構設計，在長序列中容易陷入「重複循環」
2. 沒有使用語音活動偵測（VAD）預處理，導致靜音段落也被強制轉錄
3. Medium 模型針對台灣繁體中文的優化不足

**技術依據**：
> 根據 research.md 第 86-98 行描述，Whisper 系列模型最著名的缺陷是「幻覺」。當輸入音訊為靜音、純背景音樂或噪音時，模型傾向於強行生成文字。

### 2.2 痛點二：會議記錄品質低落

**現象描述**：  
使用 Ollama + Gemma3-27b-qat（4bits 量化）模型產生會議記錄時，即使將 temperature 調至 0.1，仍出現：

- ❌ **指令遵從性不佳**：輸出格式與 system_prompt 指定的格式不符
- ❌ **會議主軸失真**：重點摘要偏離實際討論內容
- ❌ **語言混雜**：偶爾出現簡體中文或英文片段

**根本原因**：
1. 4-bit 量化導致模型能力大幅降低（約損失 15-20% 效能）
2. Gemma3 多語言特性在極低溫度下反而造成輸出不穩定
3. 上下文視窗利用不當，長逐字稿被截斷

**現有設定分析**（來自 config.yaml）：
```yaml
llm:
  ollama:
    model: "gemma3:27b-it-qat"  # 4-bit 量化版本
    num_ctx: 32768
    temperature: 0.1  # 過低可能造成 Gemma3 不穩定
```

## 3. 第一性原理分析：問題的根本原因

### 3.1 什麼是「第一性原理」思考？

「第一性原理」是把複雜問題拆解到最基本的事實，然後從零開始重新思考解決方案。

### 3.2 語音轉錄問題的第一性原理分析

```
問題：長語音轉錄出現重複字樣
  ↓ 為什麼？
Whisper 模型在長序列中產生幻覺
  ↓ 為什麼？
模型的「自迴歸」設計：每個字都依賴前面的字來預測
  ↓ 當出錯時會發生什麼？
錯誤會累積，一旦開始重複，就會持續重複
  ↓ 根本解法是什麼？
方法一：使用 VAD 將長音檔切成短片段，避免錯誤累積
方法二：使用針對台灣中文優化的模型，降低初始錯誤率
方法三：使用批次推理（Batched Inference）提升穩定性
```

### 3.3 LLM 輸出問題的第一性原理分析

```
問題：會議記錄格式不符預期
  ↓ 為什麼？
模型沒有遵循 system_prompt 的指示
  ↓ 為什麼？
4-bit 量化嚴重損害了模型的指令遵循能力
  ↓ 為什麼要用 4-bit？
為了在 RTX 4090 的 24GB VRAM 中運行 27B 模型
  ↓ 根本解法是什麼？
方法一：改用高品質量化（如 8-bit 或更少量化）
方法二：改用參數量較小但指令遵循更強的模型
方法三：使用 vLLM 等更高效的推理引擎
方法四：分段處理，避免一次餵入過長的逐字稿
```

## 4. 技術方案評估與選型

### 4.1 語音轉錄（ASR）技術選型

#### 4.1.1 模型對比表（非技術人員友善版）

| 模型名稱 | 最適合的場景 | 優點 | 缺點 | 推薦程度 |
|----------|--------------|------|------|----------|
| **Breeze-ASR-25** | 台灣會議、Podcast、日常對話 | 專為台灣中文設計，處理中英夾雜最佳 | 需要轉換格式才能使用 | ⭐⭐⭐⭐⭐ |
| Whisper Large-v3 Turbo | 多語言通用 | 速度快、資源省 | 台灣中文適配性一般 | ⭐⭐⭐ |
| FireRedASR-LLM | 純中文高精度場景 | 中文錯誤率最低 | 需要 16GB+ VRAM，不處理中英混用 | ⭐⭐⭐ |
| Whisper-medium（現用） | 簡單短音檔 | 資源需求低 | 長音檔問題嚴重 | ⭐⭐ |

#### 4.1.2 推薦方案：Breeze-ASR-25 + Faster-Whisper

**選擇理由**：

1. **專為台灣設計**  
   MediaTek Research（聯發科研究團隊）在 2025 年發布，專門針對台灣繁體中文和中英混用場景優化。

2. **性能數據**（來自 research.md）：
   - 混合語言錯誤率：比 Whisper Large V2 **降低 22%**
   - 純中文錯誤率：**降低 8%**
   - 時間戳記對齊：精度大幅提升

3. **硬體需求友善**  
   使用 INT8 量化後，僅需約 2GB VRAM，完全適合 RTX 4090

4. **已有社群轉換版本**  
   Hugging Face 上已有 `SoybeanMilk/faster-whisper-Breeze-ASR-25` 可直接使用

**技術架構圖**：

```
音檔輸入
    │
    ▼
┌─────────────────────────────┐
│  Silero VAD v6              │  ← 第一步：偵測人聲段落
│  (語音活動偵測)              │
└─────────────────────────────┘
    │ 只保留有人說話的部分
    ▼
┌─────────────────────────────┐
│  Breeze-ASR-25              │  ← 第二步：語音轉文字
│  (Faster-Whisper + INT8)    │
└─────────────────────────────┘
    │ 含時間戳記的逐字稿
    ▼
┌─────────────────────────────┐
│  WhisperX                   │  ← 第三步（可選）：精準對齊
│  (毫秒級時間戳記)            │
└─────────────────────────────┘
    │
    ▼
輸出：高品質逐字稿
```

#### 4.2.3 推薦方案：維持 Gemma3 + 優化設定

**經過第一性原理分析後的結論**：

目前的問題不是模型本身，而是**量化方式和參數設定**。Gemma3-27B 在多語言指令遵循上表現優異（支援 140+ 語言），問題出在：

1. **4-bit QAT 量化**損失過多品質
2. **temperature 0.1** 對 Gemma3 太低，反而造成不穩定
3. **缺乏針對繁中的 system prompt 優化**

**推薦的優化策略**：

```yaml
# 改用 8-bit 量化（非 QAT）
model: "gemma3:27b"  # 非 gemma3:27b-it-qat

# 調整生成參數（根據 Unsloth 官方建議）
temperature: 0.7     # 提高至推薦值
top_k: 64
top_p: 0.95

# 強化 system prompt
# 在提示詞中明確要求「台灣繁體中文」格式
```

**為什麼選擇 Gemma3 而非 Llama-3-Taiwan？**

| 考量因素 | Gemma3-27B | Llama-3-Taiwan-70B |
|----------|------------|-------------------|
| VRAM 需求 | 8-bit: ~16GB ✅ | Q4: ~35GB ❌ |
| Ollama 支援 | 官方支援 ✅ | 社群版本 ⚠️ |
| 模型穩定性 | Google 官方維護 ✅ | 學術專案 ⚠️ |
| 長期維護 | 有保證 ✅ | 不確定 ⚠️ |

**結論**：Gemma3-27B（8-bit 量化）是最適合您硬體和維護能力的選擇。

### 4.3 VAD（語音活動偵測）技術選型

**推薦使用：Silero VAD v6**

選擇理由：
1. Faster-Whisper 已內建整合，無需額外安裝
2. 輕量級（< 1MB），不佔用 GPU 資源
3. 準確率高，能有效過濾靜音和噪音

**設定參數建議**：

```yaml
vad:
  enabled: true
  threshold: 0.5          # 語音偵測閾值（0-1）
  min_speech_duration_ms: 250   # 最短語音長度
  min_silence_duration_ms: 2000  # 靜音分割閾值
  speech_pad_ms: 400      # 語音前後保留緩衝
```

### 5.3 核心配置檔案範例

#### 5.3.1 base.yaml（基礎設定）

```yaml
# =====================================================
# MeetingScribe 基礎配置
# 此檔案定義所有平台共用的預設值
# =====================================================
version: "2.0"

# ===== ASR（語音轉錄）設定 =====
asr:
  # 預設使用的模型（可被平台設定覆蓋）
  default_model: "breeze-asr-25"
  
  # VAD（語音活動偵測）設定
  vad:
    enabled: true
    threshold: 0.5
    min_speech_duration_ms: 250
    min_silence_duration_ms: 2000
    speech_pad_ms: 400
  
  # 轉錄參數
  transcription:
    language: "zh"
    beam_size: 5
```

## 6. Docker 最小成本部署策略

### 6.1 核心原則：「不重複」哲學

```
🎯 核心目標：避免浪費時間和頻寬

❌ 每次改設定都要 rebuild → 太浪費
❌ 每次 rebuild 都要重新下載模型 → 太慢
❌ 每次改前端都要重啟容器 → 太麻煩
```

### 6.2 什麼時候需要 Rebuild？什麼時候不需要？

這是最重要的觀念，請仔細閱讀：

| 變更類型 | 需要 Rebuild? | 需要重啟容器? | 說明 |
|----------|---------------|---------------|------|
| Python 依賴 (requirements.txt) | ✅ 是 | - | 新增套件需要重建 |
| 系統依賴 (apt-get install) | ✅ 是 | - | 新增系統工具需要重建 |
| Dockerfile 修改 | ✅ 是 | - | 映像檔結構改變 |
| 後端程式碼 (backend/*.py) | ❌ 否 | ✅ 是 | Volume 掛載，重啟即可 |
| 前端檔案 (frontend/*) | ❌ 否 | ❌ 否 | Volume 掛載，刷新瀏覽器 |
| 設定檔 (config.yaml) | ❌ 否 | ✅ 是 | Volume 掛載，重啟生效 |
| 環境變數 (.env) | ❌ 否 | ✅ 是 | Docker 會讀取新值 |
| ASR 模型 | ❌ 否 | ✅ 是 | 從 Volume 載入 |
| system_prompt 提示詞 | ❌ 否 | ✅ 是 | 設定檔的一部分 |

### 6.3 映像檔分層設計

我們將 Docker 映像檔設計成「三層」結構：

```
┌─────────────────────────────────────────────┐
│  Layer 3: 應用程式碼（經常變動）              │  ← Volume 掛載，不含在映像檔
│  - backend/*.py                              │
│  - frontend/*                                │
│  - config/*.yaml                             │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│  Layer 2: ASR 模型（很少變動）               │  ← Volume 持久化
│  - Breeze-ASR-25 模型權重                    │
│  - Silero VAD 模型                          │
└─────────────────────────────────────────────┘
┌─────────────────────────────────────────────┐
│  Layer 1: 基礎環境（幾乎不變）               │  ← 包含在映像檔
│  - Ubuntu 22.04 + CUDA 12                   │
│  - Python 3.11 + pip 依賴                   │
│  - FFmpeg, cuDNN 8/9                        │
│  - faster-whisper, ctranslate2 等套件        │
└─────────────────────────────────────────────┘
```

### 6.4 Volume 掛載策略

```yaml
# docker-compose 中的 volumes 設定
volumes:
  # 1. 資料目錄 - 使用者的輸入輸出
  - ../data/uploads:/app/data/uploads
  - ../data/outputs:/app/data/outputs
  - ../data/cache:/app/data/cache
  
  # 2. ASR 模型 - 使用 Named Volume 持久化
  - meetingscribe-asr-models:/app/models
  
  # 3. 開發模式 - 程式碼即時同步
  - ../backend:/app/backend          # 後端（需重啟）
  - ../frontend:/app/frontend        # 前端（刷新即可）
  - ../config:/app/config            # 設定檔（需重啟）
```

### 6.5 模型預載策略

為了避免每次 rebuild 都重新下載模型，我們採用以下策略：

**方案：Named Volume + 首次啟動下載**

```dockerfile
# Dockerfile.gpu 中的設計
# 不在 build 階段下載模型，而是在 runtime 首次使用時下載
# 下載後會存在 Volume 中，rebuild 後仍然保留

ENV HF_HOME=/app/models
ENV XDG_CACHE_HOME=/app/models

# 模型目錄會被 volume 覆蓋，首次啟動時自動下載
RUN mkdir -p /app/models
```

**Volume 持久化保證**：

```yaml
# docker-compose 中定義 named volume
volumes:
  meetingscribe-asr-models:
    driver: local
    name: meetingscribe-asr-models
    # 這個 volume 在 rebuild 時不會被刪除
    # 只有手動執行 docker volume rm 才會移除
```

### 6.6 BuildKit Cache Mount 優化

對於 Python 依賴，使用 BuildKit 的 cache mount 加速重建：

```dockerfile
# syntax=docker/dockerfile:1.4
FROM nvidia/cuda:12.3.2-cudnn9-runtime-ubuntu22.04

# 使用 cache mount 加速 pip install
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt
```

這樣即使 requirements.txt 改變，也會利用快取加速安裝。

### 6.7 開發與生產分離

**開發模式**（頻繁修改）：

```yaml
# docker-compose.override.yml（自動載入）
services:
  app:
    volumes:
      - ../backend:/app/backend      # 程式碼同步
      - ../frontend:/app/frontend    # 前端同步
      - ../config:/app/config        # 設定同步
    environment:
      - DEBUG=true
```

**生產模式**（穩定運行）：

```yaml
# docker-compose.prod.yml
services:
  app:
    # 不掛載程式碼，使用映像檔內的版本
    volumes:
      - ../data:/app/data
      - meetingscribe-asr-models:/app/models
    environment:
      - DEBUG=false
```

### 6.8 常用操作指令速查

| 情境 | 指令 | 說明 |
|------|------|------|
| 修改前端後 | 直接刷新瀏覽器 | Volume 掛載，即時生效 |
| 修改後端後 | `docker compose restart app` | 重啟容器載入新程式碼 |
| 修改設定後 | `docker compose restart app` | 重啟容器載入新設定 |
| 新增 pip 依賴 | `docker compose build --no-cache app` | 需要重建 |
| 完全重建 | `docker compose down && docker compose up -d --build` | 清理後重建 |
| 保留模型重建 | `docker compose build app` | Volume 中的模型會保留 |
| 清除模型快取 | `docker volume rm meetingscribe-asr-models` | ⚠️ 下次啟動會重新下載 |

### 6.9 映像檔大小優化

| 優化項目 | 節省空間 | 說明 |
|----------|----------|------|
| Multi-stage build | ~50% | 分離建置和運行環境 |
| 不含 ASR 模型 | ~3GB | 模型在 Volume 中 |
| 清理 apt cache | ~200MB | 移除套件快取 |
| 使用 slim 基底 | ~300MB | 精簡的 Ubuntu |

**最終映像檔大小預估**：~4GB（不含模型）

## 7. Git 版本控制策略

### 7.1 分支策略

為了保護現有穩定版本，我們採用以下分支策略：

```
main（穩定版）
  │
  ├── develop（開發主線）
  │     │
  │     ├── feature/asr-breeze-upgrade     # ASR 模型升級
  │     │
  │     ├── feature/llm-gemma-optimize     # LLM 參數優化
  │     │
  │     ├── feature/config-v2              # 新配置系統
  │     │
  │     └── feature/vad-pipeline           # VAD 管線
  │
  └── release/v4.0.0（發布候選版）
```

### 7.2 分支說明

| 分支 | 用途 | 保護規則 |
|------|------|----------|
| `main` | 生產環境穩定版 | 禁止直接推送，需 PR + 審核 |
| `develop` | 開發整合分支 | 功能分支合併目標 |
| `feature/*` | 功能開發分支 | 完成後合併至 develop |
| `release/*` | 發布準備分支 | 測試通過後合併至 main |
| `hotfix/*` | 緊急修復分支 | 同時合併至 main 和 develop |

### 7.3 Commit 規範

遵循 Conventional Commits 規範：

```
<類型>(<範圍>): <描述>

[可選的正文]

[可選的頁尾]
```

**類型定義**：

| 類型 | 說明 | 範例 |
|------|------|------|
| `feat` | 新功能 | `feat(asr): 新增 Breeze-ASR-25 模型支援` |
| `fix` | 錯誤修復 | `fix(vad): 修正長音檔靜音偵測問題` |
| `docs` | 文件更新 | `docs: 更新升級計劃文件` |
| `refactor` | 重構 | `refactor(config): 重構配置載入邏輯` |
| `test` | 測試 | `test(asr): 新增 Breeze 模型整合測試` |
| `chore` | 雜項 | `chore: 更新 Docker 基底映像` |

### 7.4 版本號規則

採用語意化版本（Semantic Versioning）：

```
v主版本.次版本.修訂版本

v4.0.0
 │ │ │
 │ │ └── 修訂版本：向下相容的錯誤修復
 │ └──── 次版本：向下相容的新功能
 └────── 主版本：不相容的 API 變更
```

**本次升級版本規劃**：

- 目前版本：`v3.5.5`
- 升級後版本：`v4.0.0`（重大架構變更）

## 9. 風險評估與緩解措施

### 9.1 風險矩陣

| 風險 | 可能性 | 影響程度 | 緩解措施 |
|------|--------|----------|----------|
| Breeze-ASR 模型下載失敗 | 低 | 高 | 準備備用模型（Whisper Large-v3） |
| Gemma3 8-bit VRAM 不足 | 低 | 中 | 可降級至 Gemma3-12B 或維持 QAT |

| RTX 4090 VRAM 不足 | 低 | 高 | 提供多種量化配置選項 |
| 升級過程影響生產環境 | 低 | 高 | 完全隔離的 feature 分支開發 |

### 9.2 回滾計劃

如果升級出現嚴重問題：

1. **立即回滾**：切換回 `main` 分支的穩定版本
2. **資料保護**：所有資料目錄（input、output、cache）與程式碼分離
3. **配置保留**：舊版 config.yaml 完整保留，不會被刪除
