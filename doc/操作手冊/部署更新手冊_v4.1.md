## 🆕 v4.7.1～v4.7.3 更新專用捷徑（2026-08-20 之後請看這裡）

這三版都**只改程式碼與提示詞**：沒有新增或變更任何**必填**環境設定鍵，也沒有動到套件或 Dockerfile，
所以更新方式和 v4.4.0 一樣——**抓最新程式 → 重啟，零下載、不需要 build**。
**舊的 `.env` 不用改**（雲端模式的預設供應商改回 Gemini 是程式內預設值，不是要你去設定的變數）。

```powershell
cd C:\meetingscribe\convert    # 依實際安裝路徑調整
git pull
cd docker
docker compose -f docker-compose-windows-gpu.yml up -d
```

（若上次更新後**沒有動過** `.env`，也可沿用較短的 `restart`；`up -d` 一律安全。）

**這三版修了什麼？**

- **v4.7.1**：修復 v4.7.0 自己引入的迴歸——整併輸出撞到長度上限（`done_reason=length`）時，
  系統原本誤判成「可重試錯誤」而重試到逾時；現在視為設計內行為，直接接受並繼續，
  長會議不再因這個誤判而變成空白紀錄。
- **v4.7.2**：修復**地端模式的公文段落編號階層**不符標準（應為「一、」→「（一）」→「1、」→
  「（1）」層層遞進；雲端模式本來就正確）。
- **v4.7.3**：①**雲端模式預設改回 Gemini**（`gemini-3.5-flash-lite`；Ollama Cloud 保留為可選供應商），
  日常使用不必做任何設定；②**雲端改成一次讀完整份逐字稿**再萃取重點（分段併發改為工程師指定才啟用，
  一般情況不用管）；③雲端模式產出的**科務會議**紀錄，句末會加註發言來源（例如「（發言者1，00:12:04）」）方便回溯；
  ④**會議日期不再亂編**：紀錄裡的年份必須是逐字稿真的說過的內容，逐字稿只說「今年／明年」或完全沒提年份時，
  一律寫「（待確認）」，不會自行推算。

**驗證**：重啟後以地端模式上傳一段會議錄音，下載的會議紀錄段落編號應層層遞進，
且長會議不應再出現「（⚠️ 僅逐字稿）」。（v4.7.3 追加）以雲端模式跑一次科務會議：
紀錄正文句末應出現發言來源標註；若逐字稿沒有提到年份，紀錄中的年份應為「（待確認）」。

> 🍎 **Mac 使用者請注意**：Mac 版另有「Apple SpeechAnalyzer 成為唯一 ASR 引擎」的變更
> （尚未發布，見 `CHANGELOG.md` 的 Unreleased 段落）；**Windows 正式主機完全不受影響**。


## 🪜 步驟六：重啟套用更新

### 📦 先用 30 秒搞懂：這次到底會不會「吃網路流量」？（重要）

> 你最在意的就是「**不要浪費網路頻寬**」。先看這個比喻，你就能完全放心：

把這套系統想成一個 **便當盒** 🍱：

- **便當盒本身**（作業系統、AI 函式庫）＝很重很大，第一次裝好後**幾乎不會再變**。
- **裡面的菜**（我們平常修改的程式碼）＝每次更新**只是換菜**。

以前 GPU 版換菜還得「重新裝一次便當盒（build）」；**現在連這都免了**——
v4.2 起程式碼改成**直接掛載進容器**（想成「菜是用夾層便當盒現夾的」），
`git pull` 抓到新的菜之後，**重啟（restart）讓它重新夾一次就好**。

只有當「**食材清單**」（套件清單 `requirements.txt`）或「**便當盒本身的設計圖**」（`Dockerfile`）真的改了——**這種情況很少，工程師會明講**——才需要 `build`（普通 build 即可，一樣不要加 `--no-cache`）。

#### 🧭 一張表看懂：要不要重建？會不會吃網路？

| 你的情況 | 要重建映像嗎？ | 會上網下載嗎？ | 對應做法 |
|---|---|---|---|
| **任何版本** + 日常更新（改程式碼／提示詞） | ❌ **不用重建** | ❌ **完全不會** | 走 **A 組或 B 組**（只要重啟） |
| 任何版本 + 工程師說「`requirements.txt` 或 `Dockerfile` 改了」 | ✅ 要重建 | 視變更而定（通常只補小套件） | 走最下面的 **備用路徑**（普通 `build`，**不要**加 `--no-cache`） |

> 🚫 **黃金守則：除非工程師明確告訴你「套件清單或 Dockerfile 改了」，否則永遠不要 build，更永遠不要自己加 `--no-cache`。** 加了 `--no-cache`＝叫電腦把整個便當盒重買一次，白白吃掉大量網路流量。

## 🆘 出問題怎麼辦？

> **黃金原則**：只要看到**紅色錯誤訊息**，先別慌、**先截圖**，停在那裡。把截圖貼給 AI 助理、或找工程師，都能快速判斷。

| 狀況 | 處理方式 |
|---|---|
| `git pull` 顯示 `not a git repository` | 程式不是用 git 部署的 → 截圖找工程師 |
| `docker ps` 的 STATUS 一直 `Restarting` | 啟動失敗 → 貼 `docker logs meetingscribe-app --tail 50` 把訊息截圖求助 |
| 重啟後網頁一直打不開 | 模型還在載入（GPU 版最多 10 分鐘）→ 先等，用 `docker ps` 看到 `(healthy)` 再試 |
| **雲端模式**報錯 / 沒反應 | ①回頭確認**步驟四**的 `.env` 是 `gemini-3.5-flash-lite`，**且改過 `.env` 後有用 `up -d`**（不是 `restart`）；②可能是 API 金鑰問題 → 暫時先用「**本地模式**」即可正常運作；③仍不行就截圖求助 |
| 會議紀錄**還是有英文 / 還是亂編** | 多半是「程式沒真的更新」：①確認步驟三 `git pull` 有看到檔名更新；②確認步驟六的 `restart` 有跑；③再重做一次步驟三＋步驟六。（**不需要** build，更不需要 `--no-cache`）|
| 想**還原**到更新前的版本 | 請工程師在專案資料夾用 `git log --oneline` 找出上一版的代碼，執行 `git reset --hard <該版代碼>`，再重做步驟六重啟 |

## 📎 附錄：給工程師看的技術摘要（你不用懂，給協助你的人看）

- **部署型態（v4.5.0 現況）**：兩份 compose（`docker/docker-compose.yml`、`docker/docker-compose-windows-gpu.yml`）皆已將 `backend/`、`frontend/` 以 volume 掛載進容器，程式碼與提示詞變更僅需 `restart` 重讀，**GPU 版亦不再需要 build**。
- **build 僅在**：`requirements.txt` 或 `Dockerfile` 變更時需要（普通 `build` 即可，逐層快取命中、僅補變更層；`--no-cache` 仍嚴禁）。v4.4.0／v4.5.0 皆**未變更**依賴或 Dockerfile，故確定零下載。
- **版本號顯示**：GPU compose 已額外掛載 `VERSION` 檔，restart 後網頁頁尾與 `/api/health` 的 `version` 會正確更新（v4.5.0）——**GPU 版的版本號已可作為更新成功的依據**。標準版未掛載 `VERSION`，restart 後功能已更新但版本顯示可能落後；若需顯示同步，rebuild 一次即可，非必要。
- **標準版 override 機制**：`docker-compose.yml` 具熱重載與啟動時自動安裝小套件的 override 設計，多數變更即時生效，restart 為保險做法。
- **模型生效優先序**：GPU compose 透過 `env_file: ../.env` 載入且自身未設 `GEMINI_MODEL`，故 `.env` 的 `GEMINI_MODEL` 會覆蓋程式內預設值——更新時一併檢查（見步驟四），現行值為 `gemini-3.5-flash-lite`（v4.5.1 起）。
- **`env_file` 凍結陷阱（v4.5.1 教訓）**：`env_file` 的內容是在容器「建立」時注入的，`docker compose restart` **不會**重讀 `.env`——這正是 v4.5.1 之前「改了 `.env` 卻不生效」的根因。凡是動了 `.env`，一律改跑 `docker compose -f docker-compose-windows-gpu.yml up -d`（Compose 偵測到設定差異會自動重建容器，秒級完成、不重載模型 volume）。同理，標準版 `docker-compose.yml` 自 v4.5.1 起不再於 `environment` 寫死 `GEMINI_MODEL`（`environment` 優先權高於 `env_file`，寫死會讓 `.env` 永遠無效）。
- **v4.4.0／v4.5.0 未新增任何環境變數**：會議模板系統（`backend/core/templates.py`）為純程式碼機制，模板定義、驗證規則、機敏防護皆內嵌於程式，不透過 `.env` 設定，`.env` 檢查步驟（步驟四）與此次更新無關。
- **v4.4.0 主要變更**：新增可擴充**會議模板系統**（`MeetingTemplate` 註冊表），內建 `general`（一般會議，行為與 v4.3.3 byte-identical）與 `procurement_evaluation`（採購評選會，`local_only=True`，前端鎖定雲端卡＋後端 `POST /api/upload` 400 雙防線）。
- **v4.7.1～v4.7.3 主要變更（純程式碼／提示詞，無新必填環境變數）**：v4.7.1 把 `done_reason=length` 從可重試例外除名（整併撞到輸出上限是設計內收斂行為，重試必然在同點截斷）；v4.7.2 修正共用提示詞與領域模板的出題階層規則（一、→（一）→1、→（1）），地端公文段落編號回復標準；v4.7.3 將雲端 provider 預設回到 `gemini`（`CLOUD_LLM_PROVIDER=ollama_cloud` 可切回 Ollama Cloud）、`CLOUD_LLM_SEGMENTED_EXTRACTION` 預設 `False`（單次呼叫整份逐字稿，`CLOUD_LLM_CHUNK_TOKENS`／`CLOUD_LLM_MAX_CONCURRENT_REQUESTS` 僅分段模式生效）、科務會議＋雲端新增發言來源標註（`speaker_traceability`）與年份依據絆索（紀錄年份必須在逐字稿出現過，否則標「（待確認）」）。三版皆未變更 `requirements.txt` 與 `Dockerfile`。
- **v4.5.0 主要變更**：新增 `section_meeting`（科務會議）模板；新增**附件輸出**基礎設施（`MeetingTemplate.attachment`）——附件由紀錄本文 Markdown 程式確定性抽表產生，不經 LLM 二次生成；新增下載端點 `GET /api/tasks/{id}/result?format=docx&doc=attachment`。
- **v4.3.3 及更早主要變更**：雲端摘要改為分段萃取＋雙輸入生成（豐富度根治）、GPU 忙碌狀態回報修正、排隊/處理階段文字中文化、Word 公文層次（章節加粗放大深藍、欄位標籤加粗）、前端 v4.3.0 全面改版、顯示文字之品牌字樣移除（docker 容器/映像/volume 識別字 `meetingscribe-app`、`meetingscribe:windows-gpu-cuda12`、`meetingscribe-whisper-models` 為基礎設施識別字，保持不變）。
- **healthcheck**：GPU 版 start period 放寬至 10 分鐘（模型載入），以 `docker ps` 之 `(healthy)` 為就緒依據。
- **驗收**：產出第一行「會議名稱：」（或所選模板對應之標題行）、無英文段／方括號模板／簡體字、未明示欄位為「（待確認）」（含年份：逐字稿未出現的年份不得寫入）、雲端＋科務會議正文句末具發言來源標註；另驗：介面階段文字全中文、GPU 忙碌顯示「使用中」、Word 具公文層次、長會議雲端產出非單薄一頁、會議類型選單正常渲染三種類型、採購評選會強制鎖定本地、科務會議出現列管資料下載按鈕。
