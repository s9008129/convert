## 1. 一句話總覽：這套機制在解什麼問題？

地端模型產會議紀錄，實測最常出現三種品質問題：

1. **漏事實**：會議真的講過（逐字稿有原文），但紀錄沒寫。
   例如金額 `600`、`13,600`、`15%` 這種數字，或整段議題被一句話帶過。
2. **捏造／沒有依據**：自創專名、數字寫錯、把發言歸給錯的人或沒依據的角色。
3. **出處標錯**：句末的「（發言者1，00:12:04）」時間戳指不到逐字稿的真實段落，
   等於沒有可查核性。
4. **固定誤辨（ASR 亂碼）**：同一類錯字每場都錯成同一個樣子（`內機`／`猜勤`／`麵`→`面`），
   校正層模型能力不足時（實測 27B 漏修 `內機→內稽`）整份紀錄跟著錯。

v4.10 的作法是：**不改提示詞、不加模型名稱分支**，改為在流程中插四道「確定性」護欄
（P4-A～P4-D，見 §2），並提供一把可重複使用的量尺（§6）驗收。
v4.10.1（P5 波）再加一道 **資料檔驅動的確定性誤辨層**（§2.5）：第 4 類問題從「靠模型猜」
變成「有登錄就一定修好」。

#### P6-A 補充（v4.10.2）——決議類 no-op 的症狀、根因與「可接受的筆記寫法」

**症狀（怎麼辨識）**

1. 跑完一場後，在 `<runtime>/backend.log` 找 pipeline metrics 行：`grep "pipeline metrics" <runtime>/backend.log`
   * `cov_expected_decision=0`＝決議期望集合是空的 → 本類別**整類不做對帳**，且 `cov_missing_decision`
     **必定也是 0**——**不要**把它讀成「決議都寫到了」（這是 no-op 的判別點）。
   * 同場其他類別通常正常（真實案例 E4／E5／E5b：`cov_expected_topic` 9／12／15、
     `cov_expected_number=9`、`cov_expected_date=4`）→ 只有決議類為 0 就是本症狀。
2. 同時會有一行 WARNING：「紀錄覆蓋率檢查：決議期望集合為空（來源：萃取筆記「議題與決議」區塊）→
   本類別不產生補強問題；請確認筆記格式，或是否只剩佔位列」（`summarization.py:2043-2048`）。
   真實 E5b 場出現三次（首輪＋每輪補強重算各一次）：`data/cache/e2e/p4-qwen27b-e5b/backend.log:269`
   ／`:350`／`:425`。
3. 真實案例（2026-09-23，0903 場、`qwen3.8-27b-splash`＋`section_meeting`）：E4／E5／E5b 連續三場
   `cov_expected_decision=0`（`data/cache/e2e/p4-qwen27b-e4/backend.log:279/284`、
   `p4-qwen27b-e5/backend.log:125`、`p4-qwen27b-e5b/backend.log:427`）；
   決議類對帳**整類靜默 no-op**（不報錯、不補強、不影響 verdict）。

**根因**：P4-A 的筆記解析器只認「一種寫法」，模型換排版就靜默退化。同一份真實筆記同時出現三種寫法：

| # | 寫法（真實例子） | 舊行為 |
|---|---|---|
| 1 | **空殼標記＋巢狀內容**：`- *決議*：`（標記行本身沒內容），決議文在下一層條列（`  - [00:12:05 發言者1（主席）]：決議文康活動形式為…`） | 只看標記行 ⇒ 期望集合恆為 0 |
| 2 | **時間＋發言者同框引用標頭**：`[00:12:05 發言者1（主席）]：…`（舊樣式只認「只有時間」） | 整段標頭（約 20 字）留在正文，LCS 比對被吃掉一半（同 E1 成因） |
| 3 | **編號型條列**：`1.`／`1)`／`（1）`（舊樣式只認 `-`／`*`／`+`） | 整份筆記換一種編號就全數抽不到 |

三者都是「筆記格式知識」，**不是模型名分支**：任何模型寫出同格式即生效（gemma 場因為剛好寫成舊格式，
同機制當時抓得到 10 條決議：`data/cache/e2e/p4-gemma31b-e5b/backend.log:523`）。

**修補形狀（v4.10.2；`7139d44` 主修補＋`4b707b6` 邊界硬化）——現在吃得下的寫法**

| 接受的寫法 | 例子 | 依據 |
|---|---|---|
| 標記行有內容 | `- *決議*：文康活動改發禮券。` | `_parse_notes_items` `summarization.py:1613` |
| 空殼標記＋巢狀條列（每列一條） | `- *決議*：`↵`  - [00:12:05 發言者1（主席）]：…` | `_collect_nested_notes_items` `:1537` |
| 整行粗體標記詞 | `- **決議**`＋下層條列 | `:1681-1687` |
| 標記同義詞 | `決議`／`決議事項`／`決議內容` | `_extract_notes_decision_items` `:1724`（`marker_keywords` `:1735`） |
| 條列符號 | `-`／`*`／`+`／`1.`／`1)`／`1、`／`（1）` | `_NOTES_ITEM_BULLET_PATTERN` `:1468` |
| 引用標頭 | `[00:12:05]`／`[00:12:05 發言者1（主席）]`／`[00:04:35] 發言者 1（主席）裁示：` | `:1462`、`_strip_notes_item_quote_prefix` `:1497` |
| 巢狀邊界 | 縮排更深才算本標記內容；同層／更淺、`#` 標題即停；區塊內其他角色標頭（`討論重點`／`裁示`／`結論`…）**連同子樹**跳過 | `_collect_nested_notes_items` `:1578-1585` |
| 共通過濾 | 剝完標頭後 <6 字、含佔位詞（`逐字稿未提及`／`（待確認）`…）、同鍵重複 → 丟棄 | `_append_notes_item` `:1595-1609`（常數 `:196`、`:219`） |

**刻意不吃（避免假期望集合）**：`*討論重點*`／`裁示`／`結論`不算決議（語意不同，放寬會產生重複期望集合與
假遺漏）；空殼標記後面沒有巢狀內容時**不假造期望**（空條目無法被滿足，只會讓補強永遠不收斂）；
議題類遇到 `- **決議**` 不把「決議」兩字當成一條議題。

### P5-A 確定性誤辨層（v4.10.1 新增）——把「一定要改的錯字」寫成資料檔

**問題**：地端模型的「校正層」是請模型自己找錯字再改；模型能力不足時（實測 27B 漏修
`內機→內稽`）就整份紀錄跟著錯。這種「固定、可列舉、有明確正確形」的錯字，不該交給模型猜。

**做法**：`data/glossary/確定性誤辨校正.txt` 一行一組 `錯=>對`，逐層在**進模型之前**先確定性修好：

| 層 | 套用點 | 影響 |
|---|---|---|
| 逐字稿清理層 | `backend/core/text_postprocess.py::apply_official_term_fixes` | 幻覺移除／去重／公務用字之後立刻修 |
| 語意校正層 | `backend/services/correction.py::correct_transcript`（逐段先修再交模型） | 送進模型的文字已是正確形 |
| 紀錄後處理層 | `backend/core/text_postprocess.py::apply_record_term_fixes`（**僅 `mode=="local"`**） | 模型若在紀錄裡又寫錯，最後再修一次 |

檔案語法（`#` 開頭或行尾皆為註解）：

```
內機=>內稽              # 一組登錄錯形
!境內機器                # 這一行是「排除複合詞」：含此字串時不得替換
```

護欄（`backend/core/glossary.py`）：
1. **長形優先**：`洪稅係統` 先於 `係統`。
2. **單字配對需有排除詞**：像 `麵=>面` 這種單字規則，必須同時登錄 `!泡麵` 之類的排除詞才放行，
   否則會被 `_pair_is_admissible()` 拒絕（避免把「泡麵」改成「泡面」）。
3. **保護詞**：同音閘門（`_would_destroy_protected_term()`，±24 字視窗）用同一份詞表推導，模型不得把
   正確詞改成錯的。
4. **無 ground truth 不登錄**：寧可留著錯字，也不要把「不確定」寫成規則（見 §8）。

**怎麼加一組**：把正確形查證到（雲端基準、原始公文、使用者確認），在檔案加一行 `錯=>對`，
在行上方用註解寫證據來源，然後跑
`DATA_DIR=/tmp/probe_scratch uv run --frozen python -m pytest tests/test_deterministic_transcript_corrections.py -q`。
**這是資料檔，不是程式碼**：LM Studio 與 Ollama、macOS 與 Windows 共用同一份檔案，換模型不用改任何程式。

### P7-A 補強輪「不回退」守衛（v4.10.3 新增）——交付的最後一版不得比中途最佳版更差

**問題**：補強輪是**整份紀錄重生成**（不是局部 patch）。實測同一場（`gemma-4-31B-it-MLX-4bit`、
`section_meeting`、0903 素材，`data/cache/e2e/p6a-gemma31b-e6/backend.log`）的數字類未涵蓋數是
`3（15:28）→ 0（15:35）→ 又 1（15:42）`——第 1 輪補回的事實被第 2 輪寫掉，使用者拿到的
「最後一版」可能是這次執行中最差的一版（成因與逐條對照見 §8-18）。

| 項目 | 內容 |
|---|---|
| 解決什麼 | **交付版本的核心覆蓋率不得低於本次執行中曾達到的最佳值**；確定性守衛（用既有逐條對帳統計），不是提示詞調參、也不是模型名分支 |
| 入口 | `backend/services/summarization.py::_summarize_with_local_pipeline` 的補強迴圈（**只在地端路徑**）；比較用 `_core_coverage_snapshot()` 取快照、`_refinement_regression_reason()`（純函式）判定 |
| 回退判定（兩條） | ①未涵蓋數變多；②未涵蓋數相同但**換項**（等量互換：原本寫到的事實被寫掉、別的補回來）。刻意**不含**忠實度與長度（避免「用捏造換事實」的反向交易） |
| 觸發回退時 | 丟棄該輪輸出、改交付最佳版本（**同分取最後一版**），並以同一組檢查（`_validate_local_record()`）**重算問題清單與 `cov_*`**——log／metrics 一律對應實際交付版本 |
| 何時不作用（不誤傷） | `LOCAL_LLM_RECORD_COVERAGE_MODE=off`、期望集合為 0 ⇒ 取不到快照（守衛不作用，也**不會**有守衛行）；期望集合中途變動（基準不同不可比）⇒ 記一行說明後停用比較。兩者都交付最後一版（`off` 仍為 byte 級回本波前） |
| 開關（一行回退） | `LOCAL_LLM_REFINEMENT_NO_REGRESSION=false`＝回本波前（交付最後一版、**無任何守衛 log 行**）；欄位＝`backend/core/config.py` 的 `LOCAL_LLM_REFINEMENT_NO_REGRESSION`（**預設 `True`**） |
| 契約修訂（重要） | `observe` 模式下**問題清單**仍零變化，但**交付版本**可被守衛換成較佳版本——「observe＝品質零變化」自此精確表述為「**問題清單**零變化」 |
| 觀測鍵 | `missing_items_<類別>`（未涵蓋項目身分）是 additive **內部**鍵：**不進** `cov_*` metrics 行、不改既有欄位格式；九個 `cov_*` 欄位（`cov_expected_*`／`cov_missing_*`／`cov_issues_added`）名稱、格式與數值語意不變 |
| 證據（截至 v4.10.3 登錄時） | 單元＋整合測試 1100 passed／2 skipped（P6-A 基線 1088）；離線重播（真實素材、呼叫產品同一份判定函式）＝**核心未涵蓋**較佳版 **26／46** vs 真實交付版 **27／46** ⇒ `guard_would_revert: true`、原因「未涵蓋數變多」；正式 E2E 場 `e2e/attempt-P7A-gemma31b-e7c` **已排定／進行中、結果尚未產生**，登錄完成前不得宣稱結論 |

**怎麼判讀守衛 log（固定契約，欄位與字串不要背錯）**

1. **每輪比較一行 info**：`地端補強不回退守衛：第 N 輪核心未涵蓋 X → Y 項（期望 Z 項）（持平，取本輪）`
   或 `（更好，取本輪）`。有這行＝守衛在作用，且本輪沒有回退。
2. **觸發回退是 warning**：`地端補強第 N 輪造成事實回退（<原因>）：核心未涵蓋 X → Y 項（期望 Z 項）→
   丟棄本輪輸出，交付最佳版本（N 字元）`；`<原因>`＝`未涵蓋數變多` 或
   `等量互換（原本已寫到的事實被寫掉 K 項）`。**看到這行＝交付版本不是最後一輪的重生成結果**，
   且 `cov_*` 已按交付版本重算。
3. **停用比較（本場剩餘輪次不再受守衛影響）**：`地端補強不回退守衛：第 N 輪取不到核心覆蓋快照
   （逐條對帳未執行）→ 本場停用比較，交付最後一版`／`…期望集合由 X 項變為 Y 項（基準不同不可比）→
   本場停用比較，交付最後一版`。看到這兩行＝本場交付最後一版，別再對照「最佳版本」預期。
4. **`cov_*` 仍照舊**：metrics 行只有九個 `cov_*` 欄位；`missing_items_*` **不會**出現在 metrics 行
   （它只存在程式內部，供集合比較）。
5. **怎麼確認「本場其實不具備觸發條件」**（沒有守衛行 ≠ 壞掉）：
   * 先確認開關：`LOCAL_LLM_REFINEMENT_NO_REGRESSION` 不是 `false`（設 `false` 時**一行守衛 log 都不會有**，這是設計）；
   * 確認本場有沒有跑補強輪：log 搜「本地摘要品質補強（第 N 輪）」——沒有＝首輪檢查就沒有問題、守衛沒有機會作用；
   * 確認逐條對帳有沒有跑：pipeline metrics 行有沒有 `cov_*`（`off` 或期望集合為 0 ⇒ 守衛不作用、也不會有守衛行）；
   * 若有補強輪、有有效 `cov_*`、也沒關開關，卻**完全沒有**守衛行 ⇒ 這不符合契約，請附 `backend.log` 回報。

## 3. 為什麼這套機制與模型無關

1. **同一條管線**：地端摘要（不論 LM Studio 或 Ollama）都走
   `backend/services/summarization.py:3171`（`_summarize_with_local_pipeline`）。
   引擎選擇在 `summarization.py:3089`（`_select_local_engine`），生成分派在
   `summarization.py:3126`（`_generate_with_local_engine`：`ollama` 分支 `summarization.py:3145`、
   `lmstudio` 分支 `summarization.py:3156`）。P4-A／B／D 的接點全部在這條管線內
   （覆蓋率 `summarization.py:3310`、忠實度 `summarization.py:3313`、
   標註吸附 `summarization.py:3451`），所以換模型不用改任何開關。
2. **兩引擎同一把尺（P4-C）**：Ollama 的取樣參數與 LM Studio 讀同一份 config
   （`summarization.py:3666` vs `summarization.py:4211`），不是各自寫死。
3. **四個槓桿零模型名分支**：本手冊撰寫時實際執行
   `rg -n "gemma|qwen" backend/core/fidelity_checks.py backend/core/text_postprocess.py`
   為零命中；獨立稽核結論亦相同
   （`.agent/tasks/T20260922-2037-02-local-model-quality-parity/e2e/portability-audit-02/report.md:9`，
   逐項表 `report.md:32-36`；後文出現的 `report.md` 均指同一檔案）。
4. **唯一與模型相關的程式**在「Ollama 選模 helper」，不是品質槓桿：
   模型別名／量化偏好 `summarization.py:4777-4781`、缺模型時的 pull 提示
   `summarization.py:4854-4855`、有效模型名解析 `summarization.py:4874-4886`。
   它們只影響「挑哪顆模型」，不影響品質判定。
5. **引擎之間的設計性差異（不是不公平）**：
   `allow_reasoning_retry` 只作用 LM Studio `summarization.py:3139-3143`；
   `expand_output_budget` 只作用 Ollama 的 `num_predict` `summarization.py:3721`。
   兩者都不改變 P4-A～D 的判定語意。

### 5.4 Windows 已知注意事項（四條）

1. **`PYTHONIOENCODING=utf-8`**

   裝了不會壞，但不再是必要條件。
3. **事實清單 JSON 存成「UTF-8 無 BOM」**
   量尺以嚴格 UTF-8 讀檔 `scripts/e2e/measure_coverage.py:869-871` 後直接
   `json.loads` `measure_coverage.py:906`；帶 BOM 會解析失敗（`Unexpected UTF-8 BOM`）

   建議改用 `[IO.File]::WriteAllText($path, $json, (New-Object Text.UTF8Encoding $false))`。
   `[UNVERIFIED]`（BOM 行為是已知的 PowerShell/.NET 行為，但未在本專案 Windows 實機驗）。
   驗法：`Format-Hex fact_checklist.json | Select-Object -First 1`，開頭不應是 `EF BB BF`。

Windows E2E 指令與 §4.3 完全相同（runner 已跨平台：時區 fallback、process group 終止、
`start_new_session=(os.name == "posix")` `run_owned_e2e.py:1941`）。

4. **詞彙表檔案用「UTF-8」存（BOM 已可容忍、Big5/ANSI 會失效）**

* 為什麼要 `DATA_DIR=...`：兩支腳本在 import backend 模組前會
  `setdefault("DATA_DIR", <repo>/data)` `measure_coverage.py:94-97`、
  `measure_record_quality.py:64-69`，日誌檔會寫到 `<DATA_DIR>/logs/app_<日期>.log`
  `backend/core/logger.py:29-47`。指定 `/tmp` 是為了不污染專案資料目錄，不是必要條件。

  用來分辨「模型真的漏寫」與「清單事實根本沒在逐字稿裡（ASR 變體／清單瑕疵）」

### 6.3 怎麼讀、什麼叫達標

1. **閘門型達標（有明確定義）**：runner `--quality-mode required` 會套用
   §2-P4-D 的五項既有門檻 `run_owned_e2e.py:179-191`，不合格時 `verdict=FAIL`，`failure_reasons` 會逐條指名（訊息格式 `run_owned_e2e.py:1014-1018`；併入 verdict `run_owned_e2e.py:1637`）。
   前提：`--template section_meeting`＋有逐字稿＋儀器版本相符 `run_owned_e2e.py:1244-1256`。
2. **覆蓋率目前沒有內建門檻（刻意）**：`--coverage-checklist` 永遠是觀察值
   `run_owned_e2e.py:1797-1800`，輸出帶 `observation_only: true`、
   `gate_effect: "none"` `run_owned_e2e.py:1031-1042`。
   要判「好／不好」，請自己跟對照組比——例如 v4.10 的實測：
   雲端基線 `coverage_all 0.8060 / core 0.8929`，地端 27B `0.7761 / 0.8571`
   （同一支音檔、同一份 checklist，`CHANGELOG.md:340-342`）。
3. **讀覆蓋率的三步**：
   * 先看 `coverage_all` 與 `coverage_core` 的**整體水位**；
   * 再看 `missing_core_ids`——逐條人工確認是「真的漏寫」還是「量尺假陰性」；
   * 有疑問時加 `--transcript` 看同一批事實是否真的存在於逐字稿。
4. **達標的限制（必讀）**：
   * 這是**字面**量尺，不是語意量尺；改寫得很好的句子可能被判漏寫（假陰性），
     關鍵詞堆砌也可能被判已涵蓋（假陽性）`measure_coverage.py:38-44`。
   * 單場是抽樣，不能宣稱穩定；要講趨勢請同一模型至少跑 2 次取中位數
     （CHANGELOG 的下一步建議 `CHANGELOG.md:377`）。
   * 量尺版本釘死：`coverage-1.0.0` `measure_coverage.py:72`、
     `tag_traceability-1.1.0` `run_owned_e2e.py:171`；跨版本數字不可直接比。

    讀法：第 1 輪補強把 3 個數字全部補回來（還順手補掉一項決議），但**同時掉了另一項決議**；
    第 2 輪補強把決議補到 0，卻**又把已補回來的 `600` 寫掉了**。⇒ 殘餘遺漏的成因**不是**
    「輪數上限（預設 2）不夠」，而是**每輪補強都重生成整份紀錄，沒有「已達標事實不得回退」的保護**。
    分辨法：把連續幾個時點的「未涵蓋」清單排出來——**遞減**＝收斂，**換項**＝回退（打地鼠）。
    對症解：**P7-A（v4.10.3）已實作「重生成後比對核心覆蓋率，回退即丟棄該輪輸出、交付最佳版本」
    的守衛**（機制與判讀法見 §2-P7-A；取捨與界線見 §8-19）。另兩個候選——補強提示夾帶
    「已達標、不得刪除」事實清單、改成局部編輯——仍**未做**。**此項不改變任何門檻，也不是 no-op。**

19. **P7-A 不回退守衛的取捨與界線（v4.10.3）** `[VERIFIED]`（單元＋離線；正式 E2E 待登錄）：
    * **只認核心覆蓋率、不認忠實度**：若某輪靠捏造換取覆蓋率提升，守衛會採用該輪
      （P4-B 忠實度絆索是唯一緩解）；且等量互換只認「新掉的項」——掉了多項但**淨改善**
      （例：3 項→1 項、其中 1 項是新掉的）**不判回退**（刻意的取捨，保住淨改善）。
    * **字面比對的繼承限制**：逐條對帳是字面量尺（§8-2）——同一事實換寫法可能被判成「漏寫」
      （例：數字寫成中文數字、議題句改寫），因而觸發回退、放棄一個其實沒有比較差的候選版本；
      回退的代價上限＝維持前一版（不會弄壞內容）。本波不處理此精度上限，僅如實登錄。
    * **等量互換判定的已證實邊界** `[VERIFIED]`：第②條是以逐條對帳的**未涵蓋項目身分**比較，
      所以某輪把同一件事**換句話說**（例：原本寫「600 元」的項目漏掉、新版寫成「六百元」補上
      該項卻漏掉另一項）也可能被判成「互換」而回退——**最壞後果只是維持前一版不換版**
      （保留較佳文字、不會弄壞內容、不會刪句），代價是可能放棄其實有進步的那一輪。
      這是刻意接受的取捨：嚴格版「掉任何一項即回退」更糟，會為保住 1 項而放棄同輪淨修好的多項。
    * **回退會放棄該輪的其他改善**；且回退後問題集合回到驅動該輪的集合 ⇒ 下一輪頂端命中既有
      不收斂保護即停止（**不多花輪次**、也不震盪）。
    * **不提升初始生成品質**、也不推論「已達雲端水準」；`observe` 的「零變化」自此只指
      **問題清單**（交付版本仍可被守衛換成較佳版本）。
