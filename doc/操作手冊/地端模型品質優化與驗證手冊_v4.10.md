# 地端模型品質優化與驗證手冊（v4.10）

> 適用對象：在 **macOS ＋ LM Studio** 或 **Windows 11 ＋ RTX 4090 ＋ Ollama** 上，
> 以地端開源模型（例如 `qwen3.8-27b-splash`、`gemma-4-31B-it-MLX-4bit`、`gemma4:31b`）
> 產生會議紀錄的人員。
>
> 本手冊描述的是 **v4.10.0「P4 波」**引進的品質機制（版本見 `CHANGELOG.md:3`）。
> 每一項機制都附上程式碼位置（`檔案:行號`），你可以直接開檔核對；
> 沒有把握的項目一律標 `[UNVERIFIED]` 並說明怎麼驗。
>
> 這套機制**不是為特定模型寫的**：所有檢查與後處理都掛在地端模型共用的同一條管線
> （`backend/services/summarization.py:2995`），所以 Mac 上的 LM Studio、辦公室的
> Ollama，甚至未來換任何地端模型，都吃同一套規則。

---

## 1. 一句話總覽：這套機制在解什麼問題？

地端模型產會議紀錄，實測最常出現三種品質問題：

1. **漏事實**：會議真的講過（逐字稿有原文），但紀錄沒寫。
   例如金額 `600`、`13,600`、`15%` 這種數字，或整段議題被一句話帶過。
2. **捏造／沒有依據**：自創專名、數字寫錯、把發言歸給錯的人或沒依據的角色。
3. **出處標錯**：句末的「（發言者1，00:12:04）」時間戳指不到逐字稿的真實段落，
   等於沒有可查核性。

v4.10 的作法是：**不改提示詞、不加模型名稱分支**，改為在流程中插四道「確定性」護欄
（P4-A～P4-D，見 §2），並提供一把可重複使用的量尺（§6）驗收。

## 3. 為什麼這套機制與模型無關

1. **同一條管線**：地端摘要（不論 LM Studio 或 Ollama）都走
   `backend/services/summarization.py:2995`（`_summarize_with_local_pipeline`）。
   引擎選擇在 `summarization.py:2913`（`_select_local_engine`），生成分派在
   `summarization.py:2950`（`_generate_with_local_engine`：`ollama` 分支 `summarization.py:2969`、
   `lmstudio` 分支 `summarization.py:2980`）。P4-A／B／D 的接點全部在這條管線內
   （覆蓋率 `summarization.py:3134`、忠實度 `summarization.py:3137`、
   標註吸附 `summarization.py:3275`），所以換模型不用改任何開關。
2. **兩引擎同一把尺（P4-C）**：Ollama 的取樣參數與 LM Studio 讀同一份 config
   （`summarization.py:3490` vs `summarization.py:4035`），不是各自寫死。
3. **四個槓桿零模型名分支**：本手冊撰寫時實際執行
   `rg -n "gemma|qwen" backend/core/fidelity_checks.py backend/core/text_postprocess.py`
   為零命中；獨立稽核結論亦相同
   （`.agent/tasks/T20260922-2037-02-local-model-quality-parity/e2e/portability-audit-02/report.md:9`，
   逐項表 `report.md:32-36`；後文出現的 `report.md` 均指同一檔案）。
4. **唯一與模型相關的程式**在「Ollama 選模 helper」，不是品質槓桿：
   模型別名／量化偏好 `summarization.py:4601-4605`、缺模型時的 pull 提示
   `summarization.py:4678-4679`、有效模型名解析 `summarization.py:4698-4710`。
   它們只影響「挑哪顆模型」，不影響品質判定。
5. **引擎之間的設計性差異（不是不公平）**：
   `allow_reasoning_retry` 只作用 LM Studio `summarization.py:2963-2967`；
   `expand_output_budget` 只作用 Ollama 的 `num_predict` `summarization.py:3545`。
   兩者都不改變 P4-A～D 的判定語意。

## 4. macOS ＋ LM Studio 操作步驟

### 4.1 前置（一次設定）

1. 在 LM Studio 開啟「本地伺服器」功能 `README.md:99`。
   程式預設連 `http://127.0.0.1:1234` `backend/core/platform_config.py:88-93`。
2. **只載入一個 LLM**（不要同時掛兩個）；否則後端會拒跑並列出候選
   `summarization.py:2885-2899`。若真的要多開，用 `LMSTUDIO_MODEL` 指定
   `config.py:68`。
3. 確認伺服器有回應（後端打的端點與此相同 `summarization.py:2836`）：
   ```bash
   curl -s http://127.0.0.1:1234/api/v1/models | head -c 400
   ```
4. 設定檔：後端只讀「環境變數／`.env`」`backend/core/config.py:1-6`，
   建議 `cp .env.example .env` 後編輯 `README.md:94`。常用變數：

| 變數 | 用途 | 預設值／位置 |
|---|---|---|
| `LOCAL_LLM_PROVIDER` | `lmstudio`／`ollama`／`auto` | `auto`；Apple Silicon 的 auto 固定解析為 `lmstudio` `platform_config.py:46-56` |
| `LMSTUDIO_BASE_URL` | LM Studio root 端點 | `http://127.0.0.1:1234` `platform_config.py:88-93` |
| `LMSTUDIO_MODEL` | 指定模型／instance | 空＝依已載入模型 `config.py:68` |
| `LOCAL_LLM_RECORD_COVERAGE_MODE` | 對帳模式 | `enforce` `config.py:287` |

### 4.2 先跑煙霧測試（不上傳、不生成）

```bash
uv run python scripts/e2e/run_owned_e2e.py --smoke
```

用途：啟動 backend → health gate → 記錄模型快照 → 乾淨結束；
`--smoke` 不上傳音檔 `scripts/e2e/run_owned_e2e.py:29-30`、`:49-50`。
若模型沒載入，這裡就會先擋下來。

### 4.3 完整 E2E（真的跑一份會議紀錄）

```bash
uv run python scripts/e2e/run_owned_e2e.py \
  --audio "/Users/<你>/Downloads/0903-科務會議.m4a" \
  --template section_meeting \
  --processing-mode local \
  --artifacts-dir .agent/tasks/<你的任務>/e2e/attempt-01 \
  --runtime-dir data/cache/e2e/attempt-01 \
  --quality-mode observe \
  --coverage-checklist .agent/tasks/T20260922-2037-02-local-model-quality-parity/quality/fact_checklist.json
```

參數名與預設值以 runner 的 argparse 為準 `run_owned_e2e.py:1735-1801`。
執行前要知道的四件事：

* `--audio` 在完整模式是必填 `run_owned_e2e.py:1803-1805`。
* `--artifacts-dir` 是**append-only**：目錄已存在就直接拒絕，不覆寫舊證據
  `run_owned_e2e.py:1876-1880`。每次跑請用新目錄名。
* preflight 會檢查 **git worktree 必須 clean** `run_owned_e2e.py:1886-1894`
  ——先把你自己未提交的變更處理掉再跑。判定是「`git status --porcelain` 一行都不准有」，
  所以**未追蹤檔案（`??`）也算髒** `run_owned_e2e.py:421-428`；
  連這份手冊本身還沒 commit 都會擋住（`--smoke` 不檢查 preflight `run_owned_e2e.py:1886`）。
* 沒給 `--runtime-dir` 時：artifacts 在 `data/cache` 內就沿用、否則自動導到
  `data/cache/e2e/<attempt 名稱>` `run_owned_e2e.py:454-470`；
  backend 的 `DATA_DIR` 預設 `<runtime>/backend_data` `run_owned_e2e.py:1833`。

## 5. Windows 11 ＋ Ollama（RTX 4090）操作步驟

### 5.1 引擎與端點

* 明確指定引擎：`LOCAL_LLM_PROVIDER=ollama` `config.py:58`。
  不指定時（`auto`）：非 macOS 的 auto 是「Ollama 優先，Ollama 不可用才試 LM Studio」
  `summarization.py:2934-2938`；Mac 的 auto 固定 LM Studio `platform_config.py:46-56`。
* `OLLAMA_BASE_URL` 程式預設是 `http://host.docker.internal:11434` `config.py:49-52`
  ——那是給「服務跑在 Docker、Ollama 跑在主機」的拓樸用的。
  **原生 Windows（不進容器）請改成 `http://127.0.0.1:11434`**；
  本 repo 的 Windows 腳本都是打 `localhost:11434`（`scripts/windows/health-check.ps1:52`、
  `scripts/start_ollama_optimized.ps1:38`）。`[UNVERIFIED]` 此組合未在本專案 Windows 實機驗證。
* 模型：`LOCAL_LLM_MODEL`（預設 `gemma4:31b` `config.py:53-56`）；先
  `ollama pull gemma4:31b` `README.md:98`（pull 指令的 helper 見 `summarization.py:4678-4679`）。

### 5.4 Windows 已知注意事項（三條）

1. **`PYTHONIOENCODING=utf-8`**
   runner 對 backend 子程序與量尺子程序會自己設定 `run_owned_e2e.py:259`、`:859`，
   所以 E2E 與量尺不受影響；但你在 PowerShell 手動跑其他 `uv run …` 指令時，
   建議先 `$env:PYTHONIOENCODING="utf-8"`，避免中文輸出亂碼。`[UNVERIFIED]`（Windows 實機未驗）。
2. **時區不需要 `tzdata`**
   v4.10 起 runner 已內建「沒有 IANA 時區資料時退回固定 +08:00」的 fallback
   `run_owned_e2e.py:81-93`（CHANGELOG `CHANGELOG.md:28-30`）。
   舊部署手冊寫「Windows 直跑需要 tzdata」（`doc/操作手冊/部署更新手冊_v4.1.md:491`）已過時；
   裝了不會壞，但不再是必要條件。
3. **事實清單 JSON 存成「UTF-8 無 BOM」**
   量尺以嚴格 UTF-8 讀檔 `scripts/e2e/measure_coverage.py:869-871` 後直接
   `json.loads` `measure_coverage.py:906`；帶 BOM 會解析失敗（`Unexpected UTF-8 BOM`）
   並以 exit 2 結束 `measure_coverage.py:907-909`。
   用 VS Code 另存「UTF-8」；PowerShell 5 的 `Out-File -Encoding utf8` 會帶 BOM，
   建議改用 `[IO.File]::WriteAllText($path, $json, (New-Object Text.UTF8Encoding $false))`。
   `[UNVERIFIED]`（BOM 行為是已知的 PowerShell/.NET 行為，但未在本專案 Windows 實機驗）。
   驗法：`Format-Hex fact_checklist.json | Select-Object -First 1`，開頭不應是 `EF BB BF`。

Windows E2E 指令與 §4.3 完全相同（runner 已跨平台：時區 fallback、process group 終止、

## 6. 品質驗證：兩把量尺怎麼用、怎麼讀、什麼叫達標

### 6.1 兩把尺的分工

| 量尺 | 量什麼 | 主要欄位 |
|---|---|---|
| `scripts/e2e/measure_coverage.py` | **事實涵蓋率**：「會議真的講過的事實，有多少被寫進紀錄」 | `coverage_all`、`coverage_core`、`missing_core_ids` `measure_coverage.py:547-550` |
| `scripts/e2e/measure_record_quality.py` | **出處標註可查核性**：標註數、是否落在真實段落、是否落在段落起點、辨別力 | `tag_traceability` 區塊；`distinct_tag_time_ratio` `measure_record_quality.py:327` |

兩支都**不呼叫** LLM／網路／LM Studio `measure_coverage.py:1-5`，同一組輸入輸出 byte 相同
（除非加 `--timestamp` `measure_coverage.py:24-25`）。

### 6.2 用法（注意 `DATA_DIR` 前綴）

```bash
# 事實涵蓋率（--record 只收 Markdown，不收 .docx measure_coverage.py:878-880）
DATA_DIR=/tmp/probe_scratch uv run python scripts/e2e/measure_coverage.py \
  --record "<runtime>/backend_data/outputs/0903-科務會議_<task_id>.md" \
  --checklist .agent/tasks/T20260922-2037-02-local-model-quality-parity/quality/fact_checklist.json \
  --transcript "<runtime>/backend_data/outputs/0903-科務會議_<task_id>_逐字稿.txt" \
  --label "qwen27b-e4" \
  --md-out /tmp/coverage_report.md

# 出處標註品質
DATA_DIR=/tmp/probe_scratch uv run python scripts/e2e/measure_record_quality.py \
  --record "<runtime>/backend_data/outputs/0903-科務會議_<task_id>.md" \
  --transcript "<runtime>/backend_data/outputs/0903-科務會議_<task_id>_逐字稿.txt" \
  --template section_meeting \
  --out /tmp/record_quality.json
```

* 為什麼要 `DATA_DIR=...`：兩支腳本在 import backend 模組前會
  `setdefault("DATA_DIR", <repo>/data)` `measure_coverage.py:94-97`、
  `measure_record_quality.py:64-69`，日誌檔會寫到 `<DATA_DIR>/logs/app_<日期>.log`
  `backend/core/logger.py:29-47`。指定 `/tmp` 是為了不污染專案資料目錄，不是必要條件。
* `--fuzzy-homophone`（預設關）：字面沒命中時才改比拼音近音，用來抓同音錯字
  `measure_coverage.py:20-23`。
* `--transcript` 的用途：多一段「同一組事實對逐字稿的涵蓋率」觀察值，
  用來分辨「模型真的漏寫」與「清單事實根本沒在逐字稿裡（ASR 變體／清單瑕疵）」
  `measure_coverage.py:15-17`。

### 6.3 怎麼讀、什麼叫達標

1. **閘門型達標（有明確定義）**：runner `--quality-mode required` 會套用
   §2-P4-D 的五項既有門檻 `run_owned_e2e.py:179-191`，不合格時 `verdict=FAIL`，`failure_reasons` 會逐條指名（訊息格式 `run_owned_e2e.py:1014-1018`；併入 verdict `run_owned_e2e.py:1637`）。
   前提：`--template section_meeting`＋有逐字稿＋儀器版本相符 `run_owned_e2e.py:1244-1256`。
2. **覆蓋率目前沒有內建門檻（刻意）**：`--coverage-checklist` 永遠是觀察值
   `run_owned_e2e.py:1797-1800`，輸出帶 `observation_only: true`、
   `gate_effect: "none"` `run_owned_e2e.py:1031-1042`。
   要判「好／不好」，請自己跟對照組比——例如 v4.10 的實測：
   雲端基線 `coverage_all 0.8060 / core 0.8929`，地端 27B `0.7761 / 0.8571`
   （同一支音檔、同一份 checklist，`CHANGELOG.md:36-39`）。
3. **讀覆蓋率的三步**：
   * 先看 `coverage_all` 與 `coverage_core` 的**整體水位**；
   * 再看 `missing_core_ids`——逐條人工確認是「真的漏寫」還是「量尺假陰性」；
   * 有疑問時加 `--transcript` 看同一批事實是否真的存在於逐字稿。
4. **達標的限制（必讀）**：
   * 這是**字面**量尺，不是語意量尺；改寫得很好的句子可能被判漏寫（假陰性），
     關鍵詞堆砌也可能被判已涵蓋（假陽性）`measure_coverage.py:38-44`。
   * 單場是抽樣，不能宣稱穩定；要講趨勢請同一模型至少跑 2 次取中位數
     （CHANGELOG 的下一步建議 `CHANGELOG.md:62`）。
   * 量尺版本釘死：`coverage-1.0.0` `measure_coverage.py:72`、
     `tag_traceability-1.1.0` `run_owned_e2e.py:171`；跨版本數字不可直接比。

### 6.4 事實清單（checklist）格式

schema 與 probes 語意見
`.agent/tasks/T20260922-2037-02-local-model-quality-parity/quality/README_measure_coverage.md`（`checklist_version`、`facts[].id/category/tier/statement/probes`；

## 8. 已知殘餘風險／限制（如實登錄）

1. **忠實度絆索只回報、不改寫**：它把問題丟進補強清單，不直接修句子
   `summarization.py:1974-1976`；補強是「整份重生成」，所以有機會被模型改好，
   也可能需要人工複核。
2. **字串判定仍有家族風險**：數字改「整串邊界」後修掉 `600`⊂`13,600`、
   行首編號 `15.` 之類的假命中 `summarization.py:1599`，但這仍是啟發式；
   議題詞級覆蓋 `summarization.py:1229` 同理。遇到可疑命中請人工看原文。
3. **覆蓋率不是閘門**：`--coverage-checklist` 永遠 observation
   `run_owned_e2e.py:1797-1800`；想把它變成驗收條件，需要另外定義門檻與校準
   （不能直接沿用來源標註的 0.95 門檻）。
4. **量尺本身有假陰性／假陽性** `measure_coverage.py:38-44`：
   同義改寫可能算漏寫、關鍵詞堆砌可能算寫到。看到 `missing_core_ids` 請先人工判讀。
5. **P4-B 觀測值未進 stored 證據**：忠實度結果目前只在 in-run log；
   跨場比較缺可攜證據 `CHANGELOG.md:56`。
6. **補強輪數尚未收斂到 1 輪**：三場實測都是 2 輪 `CHANGELOG.md:50-51`。
7. **Windows／Ollama 實機未驗** `[UNVERIFIED]`：靜態與 payload 級已驗
   （逐條未驗清單
   `.agent/tasks/T20260922-2037-02-local-model-quality-parity/e2e/portability-audit-02/report.md:106-110`），尚缺 4090 實機量測
   `CHANGELOG.md:57`。跨平台結論請以實機 A/B 為準。
8. **單場抽樣**：任何「比上次好」的宣稱至少要有 2 次同 build 取樣
   `CHANGELOG.md:62`。
9. **標註吸附的位移上限**：原時間戳離段首超過 120 秒會保留原值（仍在真實段落內），
   因此少數標註不會落在段首，這是精確度保護而非 bug `text_postprocess.py:755-761`。
