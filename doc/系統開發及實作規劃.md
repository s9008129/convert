## WebSocket 預覽一致性修復方案 - v3.3.1 新增

### 🔍 問題描述

用戶反映的症狀：
- **雲端模式**：任務完成時，網頁上實時顯示結果預覽（前 2000 字）
- **地端模式**：任務完成時，網頁上只顯示"已完成，請下載檔案查看詳細內容"

**問題本質**：用戶體驗不一致，儘管後端都在發送完整結果

### 🧠 第一性原理分析

#### 時序問題
```
時刻 T                事件                              WebSocket 消息
────────────────────────────────────────────────────────────────────
T0   上傳文件         ┌─────────────────────────────┐
     （雲端或地端）   │ 後端：任務已加入隊列        │ ProgressMessage
                      │ status: queued              │ preview: null
                      └─────────────────────────────┘

T1   開始處理         ┌─────────────────────────────┐
                      │ 後端：正在轉錄              │ ProgressMessage
                      │ status: transcribing        │ preview: null
                      └─────────────────────────────┘

T2   處理完成         ┌─────────────────────────────┐
     （地端快速完成）  │ 後端：任務完成              │ ProgressMessage
                      │ status: completed           │ preview: result_content
                      │ 會立即寫入結果文件          │
                      └─────────────────────────────┘
                      
T3   前端 WebSocket   ┌─────────────────────────────┐
     連接建立         │ WebSocket 端點連接到任務    │ 讀取當前任務狀態
     （遲於完成）      │ 任務已完成！但...          │ ❌ 未讀取文件的預覽
                      └─────────────────────────────┘
```

#### 根本原因
在 `backend/api/websocket.py` 的 `websocket_endpoint()` 函數中：

```python
# ❌ 修復前：缺少 preview 邏輯
message = ProgressMessage(
    task_id=task_id,
    status=task.status,      # 此時可能是 COMPLETED
    progress=task.progress,
    stage=task.stage,
    message=f"目前狀態: {task.status.value}",
    eta_seconds=task.estimated_wait_seconds,
    queue_position=task.queue_position,
    queue_total=queue_status.total_queued
    # ❌ 沒有 preview 參數！
)
```

當任務已完成但 WebSocket 剛連接時，會發送沒有 `preview` 的消息。前端檢查 `if (message.preview)` 時為 false，就顯示"已完成，請下載..."

### ✅ 修復方案

#### 1. 新增輔助函數
```python
def _get_result_preview(task_id: str, original_filename: str) -> Optional[str]:
    """
    從已完成的結果文件讀取預覽內容（前 2000 字）
    
    特點：
    - 只讀取已存在的文件
    - 異常安全，返回 None 如果失敗
    - 無文件修改，無副作用
    """
```

#### 2. 修改兩處 WebSocket 消息構建邏輯

位置 1：初始連接時（第 119-121 行）
```python
# ✅ 修復後
preview = None
if task.status == TaskStatus.COMPLETED:
    preview = _get_result_preview(task_id, task.original_filename)

message = ProgressMessage(
    # ... 其他欄位
    preview=preview  # ✅ 包含預覽
)
```

位置 2：心跳超時時（第 149-151 行）
```python
# ✅ 修復後：完全相同邏輯
preview = None
if task.status == TaskStatus.COMPLETED:
    preview = _get_result_preview(task_id, task.original_filename)

message = ProgressMessage(
    # ... 其他欄位
    preview=preview  # ✅ 包含預覽
)
```

### 📊 修復效果驗證

#### 修復前後對比
| 測試場景 | 修復前 | 修復後 |
|---------|--------|--------|
| WebSocket 快速連接 | 顯示預覽 ✅ | 顯示預覽 ✅ |
| WebSocket 遲到連接 | 顯示"下載..." ❌ | 顯示預覽 ✅ |

#### 用戶體驗
修復後，地端和雲端模式都能：
1. ✅ 完成時立即顯示結果預覽（前 2000 字）
2. ✅ 提供"複製文本"按鈕

### 🔧 技術實作細節

#### Layer 1: Whisper 轉錄層優化

```python
# 修改前（問題代碼）
traditional_chinese_prompt = "以下是台灣繁體中文的會議逐字稿，請使用正體中文輸出。"

# 修改後（最佳實踐）
traditional_chinese_prompt = "這是一場專業會議的逐字記錄，討論主題包含專案進度、決議事項。"
```

**改善原理**：Whisper 的 `initial_prompt` 應該是「範例內容」而非「指令」，使用範例內容格式可引導模型輸出類似風格，而不會被混入輸出中。

#### Layer 2: Prompt Engineering 重構

**改善前**：使用 XML 標籤結構（COSTAR-X 框架）
- 對雲端 API 友善，但地端模型解析較差

**改善後**：使用純 Markdown 結構
- 步驟化工作流程說明
- 明確的輸出格式範例
- 添加「直接輸出」規則，避免 LLM 加入開場白

#### Layer 3: Ollama API 參數優化

```python
# 修改前
"options": {
    "temperature": 0.1
}

# 修改後
"options": {
    "temperature": 0.1,       # 低溫提高格式遵循度
    "top_p": 0.9,             # 控制輸出多樣性
    "top_k": 40,              # 限制候選詞數量
    "repeat_penalty": 1.15,   # 防止重複

## Gemini API 最小成本連線測試方案 - v3.2.0 新增

### 📊 第一性原理分析

#### 1. 需求定義
- **現象**：使用者點選「雲端模式」時，系統僅檢查 API Key 存在性（無實際連線）
- **問題**：無法確保 Gemini API 真正可用，用戶可能在任務執行時才發現連線失敗
- **約束**：多用戶場景 + API 配額限制（1,000 次/天）+ 需要真正的連線測試

#### 2. 根本成本來源分析
```
每個使用者在會議轉錄流程中的 API 調用：
├─ 初始化檢查    → 1 次 API 調用（進入系統時）
├─ 模式切換      → 1 次 API 調用（選擇雲端模式時）
├─ 實際摘要      → 1 次 API 調用（執行任務時）
└─ 重試（失敗時）→ 0-N 次 API 調用

配額危機：
- 100 位日活用戶 × 3 次平均調用 = 300 次/天
- 假設 20% 使用雲端 = 20 用戶 × 3 次 = 60 次/天
- 如每次初始化都檢查 = 20 次不必要的調用
- 總計需求：60 次最小調用，檢查調用應接近 0
```

#### 3. 最小成本方案：分層智能檢查

```
┌─────────────────────────────────────────────┐
│  層級1: 本地檢查（0 成本）                    │

│  ✓ 環境變數讀取                              │

│  ✓ 結果快取 24 小時                         │
│  ✓ 多用戶共用快取結果                        │

│  ✓ 估計成本：~0.001 tokens/次                │

```python
# backend/services/summarization.py

class SummarizationService:
    def __init__(self):
        # 快取配置
        self._gemini_health_check_cache = {
            "last_check_time": None,      # 上次檢查時間
            "status": None,                # 檢查結果（True/False）
            "ttl_seconds": 86400           # 24小時快取
        }
    
    def check_gemini_available(self) -> bool:
        """
        層級1：本地檢查（0成本）
        只驗證 API Key 存在性，不進行實際連線
        """
        try:
            self._get_gemini_api_key()
            return True
        except ValueError:
            return False
    
    async def check_gemini_health(self, force_refresh: bool = False) -> bool:
        """
        層級2：每日健康檢查（1次API調用/天）
        
        特點：
        - 自動快取24小時結果
        - 多用戶共用快取（節省調用）
        - force_refresh=True 強制重新檢查
        """
        now = datetime.now()
        cache = self._gemini_health_check_cache
        
        # 快取有效期檢查
        if not force_refresh and cache["last_check_time"]:
            age_seconds = (now - cache["last_check_time"]).total_seconds()
            if age_seconds < cache["ttl_seconds"] and cache["status"] is not None:
                log.debug(f"使用快取結果（年齡: {age_seconds:.0f}秒）")
                return cache["status"]
        
        # 執行 API 檢查：使用最輕量的端點
        log.info("執行 Gemini API 健康檢查...")
        try:
            if not self.check_gemini_available():
                cache["status"] = False
                cache["last_check_time"] = now
                return False
            
            # 調用 models.list() - 極輕量，估計 ~0.001 tokens
            client = self._get_gemini_client()
            response = client.models.list()
            result = len(list(response.models)) > 0
            
            cache["status"] = result
            cache["last_check_time"] = now
            log.info(f"Gemini 健康檢查：{'✓ 可用' if result else '✗ 不可用'}")
            return result
        except Exception as e:
            log.warning(f"Gemini 檢查失敗: {e}")
            cache["status"] = False
            cache["last_check_time"] = now
            return False
    
    def reset_gemini_health_cache(self):
        """重置快取（環境變數變更時調用）"""
        self._gemini_health_check_cache = {
            "last_check_time": None,
            "status": None,
            "ttl_seconds": 86400
        }
```

# 任務狀態（v2.1 新增 QUEUED 狀態）
class TaskStatus(str, Enum):
    QUEUED = "queued"          # 排隊中（v2.1 新增）
    PENDING = "pending"        # 等待處理
    UPLOADING = "uploading"    # 上傳中
    TRANSCRIBING = "transcribing"  # 轉錄中
    SUMMARIZING = "summarizing"    # 生成摘要中
    COMPLETED = "completed"    # 已完成
    FAILED = "failed"          # 失敗

# 任務資訊（v2.1 更新）
class TaskInfo(BaseModel):
    task_id: str
    filename: str
    status: TaskStatus
    progress: float  # 0-100
    stage: str
    queue_position: Optional[int]     # 排隊位置（v2.1 新增）
    estimated_wait: Optional[int]     # 預估等待秒數（v2.1 新增）
    user_prompt: Optional[str]        # 使用者自訂 prompt（v2.1 新增）
    created_at: datetime
    completed_at: Optional[datetime]
    error_message: Optional[str]

# 處理結果
class TranscriptionResult(BaseModel):
    task_id: str
    filename: str
    transcript: str      # 原始逐字稿
    summary: str         # 摘要（Markdown 格式）
    duration_seconds: float
    processing_time: float
    word_count: int
    model_info: dict
    user_prompt_used: Optional[str]   # 使用的 prompt（v2.1 新增）

# WebSocket 進度訊息（v2.1 更新）
class ProgressMessage(BaseModel):
    task_id: str
    status: TaskStatus
    progress: float
    stage: str
    message: str
    eta_seconds: Optional[int]
    queue_position: Optional[int]     # 排隊位置（v2.1 新增）
    queue_total: Optional[int]        # 排隊總數（v2.1 新增）

# 排隊狀態（v2.1 新增）
class QueueStatus(BaseModel):
    total_queued: int                 # 排隊總數
    processing_count: int             # 正在處理的任務數
    estimated_wait_seconds: int       # 預估等待時間
    max_concurrent: int               # 最大同時處理數

# 上傳請求（v2.1 新增）
class UploadRequest(BaseModel):
    user_prompt: Optional[str] = None  # 使用者自訂 prompt
    processing_mode: str = "local"     # local 或 cloud

```python
# backend/services/gemini_client.py

import os
from openai import OpenAI

class GeminiClient:
    """
    Gemini API 客戶端
    使用 OpenAI 相容介面存取 Gemini API
    """
    
    def __init__(self):
        # API Key 從環境變數取得（安全方式）
        api_key = os.environ.get("GEMINI_API_KEY")
        if not api_key:
            raise ValueError("未設定 GEMINI_API_KEY 環境變數")
        
        self.client = OpenAI(
            api_key=api_key,
            base_url="https://generativelanguage.googleapis.com/v1beta/openai/"
        )
        self.model = os.environ.get("GEMINI_MODEL", "gemini-2.5-flash-lite")
    
    def summarize(self, transcript: str, system_prompt: str) -> str:
        """生成會議摘要"""
        response = self.client.chat.completions.create(
            model=self.model,
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": f"請整理以下會議逐字稿：\n\n{transcript}"}
            ]
        )
        return response.choices[0].message.content

### 💻 裝置偵測程式碼

```python
# backend/services/device_detector.py

import logging
import subprocess
from enum import Enum
from typing import Tuple, Optional

logger = logging.getLogger(__name__)


class DeviceType(Enum):
    CUDA = "cuda"
    MPS = "mps"
    CPU = "cpu"


class DeviceDetector:
    """
    智能裝置偵測器
    自動偵測最佳運算裝置，並支援動態降級
    """
    
    def __init__(self):
        self.current_device: Optional[DeviceType] = None
        self.fallback_count = 0
    
    def detect_best_device(self) -> Tuple[DeviceType, str]:
        """
        偵測並回傳最佳可用裝置
        
        Returns:
            (裝置類型, 計算精度)
        """
        # 優先嘗試 CUDA
        if self._check_cuda():
            self.current_device = DeviceType.CUDA
            logger.info("✅ 偵測到 NVIDIA GPU，使用 CUDA 加速")
            return DeviceType.CUDA, "float16"
        
        # 嘗試 MPS (Apple Silicon)
        if self._check_mps():
            self.current_device = DeviceType.MPS
            logger.info("✅ 偵測到 Apple Silicon，使用 MPS 加速")
            return DeviceType.MPS, "float16"
        
        # 降級到 CPU
        self.current_device = DeviceType.CPU
        logger.warning("⚠️ 無 GPU 可用，使用 CPU 模式（處理速度較慢）")
        return DeviceType.CPU, "int8"
    
    def _check_cuda(self) -> bool:
        """檢查 CUDA 是否可用"""
        try:
            result = subprocess.run(
                ["nvidia-smi", "--query-gpu=memory.free", "--format=csv,noheader,nounits"],
                capture_output=True, text=True, timeout=10
            )
            if result.returncode == 0:
                free_memory = int(result.stdout.strip().split('\n')[0])
                # 至少需要 4GB VRAM
                return free_memory >= 4000
        except Exception as e:
            logger.debug(f"CUDA 偵測失敗：{e}")
        return False
    
    def _check_mps(self) -> bool:
        """檢查 Apple MPS 是否可用"""
        try:
            import torch
            return torch.backends.mps.is_available()
        except Exception:
            return False
    
    def fallback_to_cpu(self) -> Tuple[DeviceType, str]:
        """
        降級到 CPU 模式
        當 GPU 處理失敗時呼叫
        """
        self.fallback_count += 1
        self.current_device = DeviceType.CPU
        logger.warning(f"⚠️ 第 {self.fallback_count} 次降級到 CPU 模式")
        return DeviceType.CPU, "int8"
    
    def get_device_info(self) -> dict:
        """取得目前裝置資訊"""
        return {
            "current_device": self.current_device.value if self.current_device else "unknown",
            "fallback_count": self.fallback_count,
            "gpu_available": self._check_cuda() or self._check_mps()
        }
```

## 風險評估與對策

### ⚠️ 潛在風險（v2.0 更新）

| 風險 | 機率 | 影響 | 對策 |
|------|------|------|------|
| **影響其他 Docker 服務** | 低 | **極高** | 獨立網路、資源限制、嚴格隔離 |
| **Docker 映像過大** | 高 | 中 | 使用多階段建構、精簡依賴 |
| **GPU 驅動不相容** | 中 | 高 | 智能降級機制，自動切換到 CPU |
| **Ollama 服務不可用** | 低 | 中 | 提供雲端模式作為備援 |
| **Gemini API 費用超支** | 低 | 低 | 預設使用本地模式，雲端模式需手動選擇 |
| **記憶體不足** | 中 | 高 | 限制同時處理的任務數、資源上限 |
| **長音訊處理失敗** | 低 | 中 | 實作分段處理和重試機制 |

### 🛡️ 緩解措施

```
風險 0（首要）：影響其他 Docker 服務
─────────────────────────────────────────────────────────
對策：
• 使用獨立的 Docker 網路 (meetingscribe-isolated-net)
• 設定 CPU 和記憶體資源上限
• 不共享任何 Volume 或網路
• 使用 host.docker.internal 連接主機 Ollama

驗證方式：
• 啟動/停止/重啟 MeetingScribe 時，其他服務完全不受影響
• 資源使用不會超過設定上限
```

```
風險 1：Docker 映像過大
─────────────────────────────────────────────────────────
對策：
• 使用多階段建構，分離建構環境和執行環境
• 僅安裝必要的系統套件
• 不包含 Ollama（使用主機已安裝的）

預期效果：映像大小約 8-10GB（含 Whisper 模型）
```

```
風險 2：GPU 驅動不相容或資源不可用
─────────────────────────────────────────────────────────
對策：
• 啟動時自動偵測最佳可用裝置
• 執行時監控 GPU 狀態，異常時自動降級
• 使用者會收到降級通知

預期效果：即使 GPU 完全不可用，服務仍能以 CPU 模式運行
```

```
風險 3：本地 Ollama 服務不可用
─────────────────────────────────────────────────────────
對策：
• 啟動時檢查 Ollama 服務狀態
• 若 Ollama 不可用，提示使用者切換到雲端模式
• 健康檢查腳本可快速診斷問題

預期效果：使用者可選擇雲端模式繼續使用
```
